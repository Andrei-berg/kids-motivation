# Phase 09.3: Code Review Report

**Reviewed:** 2026-09-19T15:06:06Z
**Depth:** standard
**Files Reviewed:** 21
**Status:** issues_found

## Summary

Phase 09.3 swaps `KidDayFillForm`'s render tree for the new sticky-summary layer
(`StickySummaryBar`, `QuickRow`, `InlinePanelRow`, the decomposed `day-blocks/*`
renderers) and adds the self-serve `children.fill_style` column/action. The new
pure logic (`lib/kid/day-fill-progress.ts`) is correct and well covered by its
unit tests; the migration and its verify script are sound and idempotent; the
`fill-style` server action is correctly guarded (`requireFamilyMember` +
`authorizeChildAction`, same pattern as the money routes) and does not
reintroduce any client-side wallet write — no CLAUDE.md money-mutation
violation found. i18n key parity between `en.json`/`ru.json` is intact (1761/1761,
no missing keys either direction), and every new class referenced by the
reviewed components (`coin-flyup-*`, `kid-mood-pop`, `kid-skeleton`) exists in
`globals.css` with the documented reduced-motion double-guard.

However, while tracing `KidDayFillForm`'s lock logic against the back-fill
feature it renders for (`children.backfill_mode` / `WeekStrip`'s 'fill' action),
I found that the form's `isLocked` gate is date-only and does not account for
backfill mode at all. This makes the "kid fills a missed day" flow — the entire
point of `backfill_mode` 'open' and approved 'request' rows — completely
non-functional through this form: tapping "fill" on a past day renders every
row disabled and replaces the Save button with a "day is closed" message, so
nothing can ever be entered or submitted. This predates Phase 09.3 (the check
is unchanged since the form's original April commit and was not touched by the
09.3-09 or the 2026-09-10 back-fill feature commit), but it lives entirely
inside a file in this phase's scope and is a live, provable defect in the code
being shipped, so it is reported as a blocker below.

## Critical Issues

### CR-01: Back-fill "fill a missed day" is unusable — `isLocked` ignores `backfill_mode`

**File:** `components/kid/KidDayFillForm.tsx:244-247` (gate), with every
interactive control disabled by it (e.g. `:537`, `:591-592`, `:607-608`,
`:612-613`, `:626-627`, `:1200`, `:1438-1442`) and the submit button removed
entirely by it (`:1481-1486`).

**Issue:** `isLocked` is computed purely from the date:

```ts
const isLocked = useMemo(() => {
  const today = localDateString()
  return date < today
}, [date])
```

This has no awareness of `children.backfill_mode`/`backfill_days`. But
`WeekStrip` (`components/kid/WeekStrip.tsx:81-89`) explicitly invites the kid
to tap a past day and fill it right now, in two cases:
- `backfillMode === 'open'` and the day is inside the `backfill_days` window
  → `action = 'fill'`
- `backfillMode === 'request'` and the day's request `status === 'approved'`
  → `action = 'fill'`

Tapping either cell calls `onFillDay(d)` → `app/kid/(app)/day/page.tsx`'s
`handleFillDay` → `setSelectedDate(d)`, which is passed straight through as
`date` to `KidDayFillForm`. Because `date < today` is true for any of these
cells, `isLocked` is `true` the moment the form renders for that date — every
`QuickRow`/`InlinePanelRow`/mood button renders `disabled`, and the submit
button branch is replaced by:

```tsx
{isLocked ? (
  <div>...{t('kidFillForm.dayLocked')}</div>   // "🔒 Day is closed for editing"
) : ( <button onClick={handleSubmit}>...</button> )}
```

So the kid literally cannot toggle a single field or save, for either
back-fill mode — even though `/api/wallet/award` (`app/api/wallet/award/route.ts:176-205`,
not in this phase's scope but confirms the intent) explicitly implements a
gate that *credits* a child-initiated non-today award under exactly these two
conditions. The server side of the feature is ready to accept these saves;
the client-side lock prevents them from ever being produced. This is
data-loss-adjacent (the entire "kid catches up on a missed day" flow silently
does nothing but show a misleading "locked" message) and directly contradicts
the documented feature behavior (`components/kid/WeekStrip.tsx:4-8`, the
`2026-09-10` back-fill feature commit message, and the `kid-day-screen-back-fill`
project memory entry).

**Fix:** Thread the child's back-fill eligibility into the lock check instead
of a bare date comparison, e.g. pass `backfillMode`/`inWindow`/`requestStatus`
(or simply an `allowBackfillFill: boolean` computed by the caller, mirroring
`WeekStrip`'s own `action === 'fill'` condition) down to `KidDayFillForm` and
OR it into `isLocked`:

```ts
const isLocked = useMemo(() => {
  const today = localDateString()
  if (date >= today) return false
  return !allowBackfillFill // only a day the kid is authorized to back-fill stays open
}, [date, allowBackfillFill])
```

`allowBackfillFill` should be computed the same way `WeekStrip` computes
`action === 'fill'` for this date (open mode + in-window, or request mode +
`approved`), so the two components can never disagree about which past days
are fillable.

## Warnings

### WR-01: `todayLabel()` uses browser-local time, not the app's canonical "today"

**File:** `app/kid/(app)/day/page.tsx:33-36` (used at `:271` and `:490`)

**Issue:** CLAUDE.md is explicit that "today" must be computed via
`localDateString()` (fixed UTC+3), never a bare `new Date()`, because the two
can disagree for part of the day depending on the client's timezone. `today`
itself (`page.tsx:87`) correctly uses `localDateString()`, but the display
helper does not:

```ts
function todayLabel(language: string): string {
  const locale = language === 'ru' ? 'ru-RU' : 'en-US'
  return new Date().toLocaleDateString(locale, { weekday: 'short', day: 'numeric', month: 'short' })
}
```

For a client whose device timezone differs from UTC+3 (or straddles a
midnight boundary), the label shown next to the level/streak header, and on
the "day filled" summary card, can show a different calendar date than the
`today`/`selectedDate` the rest of the screen is actually operating on.

**Fix:**
```ts
function todayLabel(language: string): string {
  const locale = language === 'ru' ? 'ru-RU' : 'en-US'
  return new Date(localDateString() + 'T12:00:00').toLocaleDateString(locale, { weekday: 'short', day: 'numeric', month: 'short' })
}
```

### WR-02: Mobile "day complete" summary always shows *today's* label, even for a back-filled day

**File:** `app/kid/(app)/day/page.tsx:490`

**Issue:** The mobile "filled" celebration card renders `{todayLabel(language)}`
unconditionally under the "great job" heading, with no branch for
`isBackfill`. Once CR-01 is fixed and a kid can actually complete a back-filled
day, this card will show today's date underneath a confirmation for a day that
is not today — misleading. (The desktop variant at `:337-366` does not have
this problem since it never renders a date there.)

**Fix:** Use `selectedDate` (formatted the same way) instead of `today` when
`isBackfill` is true, mirroring the existing `backfillBanner` copy already
built for this state (`:437-444`).

### WR-03: `useCoinAnimation.trigger()` has no unmount cleanup for its removal timer

**File:** `components/kid/CoinAnimation.tsx:30-38`

**Issue:**
```ts
const trigger = useCallback((amount: number, anchor?: FlyupAnchor | null) => {
  if (amount === 0) return
  const id = ++counter.current
  const x = 30 + Math.random() * 40
  setFlyups(prev => [...prev, { id, amount, x, ...(anchor ? { anchor } : {}) }])
  setTimeout(() => {
    setFlyups(prev => prev.filter(f => f.id !== id))
  }, 1200)
}, [])
```
`KidDayFillForm` fires a flyup immediately before navigating away from the
form on save (`triggerCoinFlyup(coinsPreview)` then `creditAwardAndFinish()`,
which on success calls `onSaved(...)` and the parent unmounts the form). The
1200ms cleanup `setTimeout` is not cancelled on unmount, so `setFlyups` can run
against an unmounted `useCoinAnimation` owner after every save — a stray
state update outside React's lifecycle (dev-mode warning today; a source of
subtle bugs if this hook is ever reused somewhere with real side effects tied
to `flyups`).

**Fix:** Track timers in a ref and clear them on unmount:
```ts
const timers = useRef<Set<ReturnType<typeof setTimeout>>>(new Set())
useEffect(() => () => { timers.current.forEach(clearTimeout); timers.current.clear() }, [])
// inside trigger():
const timer = setTimeout(() => {
  setFlyups(prev => prev.filter(f => f.id !== id))
  timers.current.delete(timer)
}, 1200)
timers.current.add(timer)
```

## Info

### IN-01: Duplicate `@keyframes` definitions in `globals.css`

**File:** `app/globals.css` — `@keyframes fadeIn` is defined three times
(`:460`, `:532`, `:4484`), `@keyframes spin` is defined three times (`:635`,
`:914`, `:4495`), all with identical (or functionally identical) bodies.

**Issue:** Harmless (the last declaration simply wins) but is dead/duplicate
CSS left over from repeated copy-paste across the legacy stylesheet's
sections — adds noise and risk of the copies drifting apart later.

**Fix:** Keep one canonical `@keyframes fadeIn`/`@keyframes spin` near
`:root`/typography and delete the later re-declarations.

### IN-02: `ProfileSheet`'s fill-style save failure is silently swallowed

**File:** `components/kid/ProfileSheet.tsx:69-80`

**Issue:**
```ts
async function handleFillStyleTap() {
  if (!child?.id || savingFillStyle) return
  setSavingFillStyle(true)
  try {
    await updateChildFillStyle(child.id, 'sticky-summary')
    await load()
  } catch (err) {
    console.warn('updateChildFillStyle failed', err)
  } finally {
    setSavingFillStyle(false)
  }
}
```
If `updateChildFillStyle` throws (e.g. a transient network error, or the
server-side `authorizeChildAction` guard rejecting an unexpected `child.id`),
the only feedback is a console warning — the button just stops showing its
saving state with no visible indication to the child that nothing happened.
Low-impact today since this phase only offers one style (the action is a
no-op update to the value it likely already has), but the pattern will need
real user-facing error handling once Phase 9.4 makes this a genuine choice
between three styles.

**Fix:** Surface a lightweight inline error (or toast) on catch, consistent
with `KidDayFillForm`'s own `saveError` pattern.
