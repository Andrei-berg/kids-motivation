# Phase 9.3: dayform-default - Context

**Gathered:** 2026-09-19
**Status:** Ready for planning

<domain>
## Phase Boundary

Add a persisted, changeable per-child `fill_style` preference (`tile-sheet` / `story-stepper` /
`sticky-summary`), and build the **sticky-summary** style as the default day-fill experience:
a persistent completion ring + live coin total on screen at all times; binary categories toggle
with one tap directly on their row (no sheet/accordion); multi-value categories expand a small
inline panel in place; every category fill shows a floating "+N coins" (or "-N coins" for a
loss) that rises/fades and ticks the running total.

`tile-sheet` and `story-stepper` (DAYFORM-02/03) are **not built in this phase** — they belong
to Phase 9.4 (dayform-styles), which depends on this phase. This phase only needs the
`fill_style` preference field/control to exist and default correctly (DAYFORM-01, DAYFORM-06),
and the sticky-summary style itself to be fully real (DAYFORM-04, DAYFORM-05 as they apply to
this one style — the other two styles get DAYFORM-05 compliance in Phase 9.4).

Today's `KidDayFillForm.tsx` is a single-open accordion (`CollapsibleRow` sections, one open at a
time via `openId` state) with a `coinsPreview` client estimate that only flies up once at final
save. This phase replaces that interaction/render layer with the sticky-summary model while
reusing the form's existing state, validation, save, and `/api/wallet/award` call logic
unchanged (see Decisions → "Reuse vs. rebuild").

</domain>

<decisions>
## Implementation Decisions

### `fill_style` scope in this phase
- **D-01:** The `fill_style` control shows **only `sticky-summary`** as a real, selectable
  option in Phase 9.3 — `tile-sheet` and `story-stepper` are not shown/offered yet (no
  "coming soon" UI, no silent-fallback UI for them either). They appear once Phase 9.4 ships
  their actual implementations. This means the Phase 9.3 control can be as simple as a
  confirmation that `sticky-summary` is active, or a single-option picker — not a 3-way
  selector yet. DAYFORM-01's literal "shows a control with all 3 styles" is satisfied
  incrementally: fully met after Phase 9.4, not required to be met by 9.3 alone.
- **D-02 (DAYFORM-06, already locked by requirements):** A child with no explicit `fill_style`
  row/value defaults to `sticky-summary`. Schema default should be `sticky-summary` (mirrors the
  `backfill_mode` column pattern: `TEXT NOT NULL DEFAULT '...'` + CHECK constraint).

### Where the control lives
- **D-03:** The `fill_style` control is **self-serve, in the kid's own `ProfileSheet`**
  (`components/kid/ProfileSheet.tsx`) — not in Parent Center Settings, not parent-gated. This
  mirrors the avatar-picker pattern (`AvatarPicker.tsx` / `app/kid/actions/avatar.ts`), not the
  `backfill_mode` pattern (which is a parent trust/policy decision). Rationale: fill style is a
  personal UI-taste preference the kid should control freely, unlike backfill policy which is a
  parent decision about trust.
- **D-04:** The write path must follow `app/kid/actions/avatar.ts` exactly: a `'use server'`
  action using `requireFamilyMember()` + `authorizeChildAction(admin, member, childId)` +
  `createAdminClient()`, updating `children.fill_style` with the service-role client. `children`
  is not directly client-writable via RLS for this kind of field (per the avatar action's
  comment) — do not attempt a direct Supabase client `.update()` from `ProfileSheet`.

### Binary-row vs. inline-panel mapping (real categories, not the sketch's simplified example)
- **D-05:** **Binary one-tap rows** (toggle switch, directly on the row, re-tappable — see D-10):
  room-task completion (existing 60%-threshold logic unchanged), each individual extra activity
  from the activities checklist (its own row, not grouped under one shared "Activities" panel),
  and each individual custom day-block (its own row). This is a deliberate broadening of
  DAYFORM-04's literal "room, behavior" example: any category whose real data shape is a simple
  yes/no gets the one-tap treatment.
- **D-06:** Behavior is **not** a true binary switch given the real data model (Phase 5.9
  replaced a single good/bad flag with multi-select behavior-tags that get proposed and then
  parent-approved via `behavior_marks`). The behavior row is a single tap target on the main row
  list (matching DAYFORM-04's "no full sheet/accordion" principle), but tapping it **expands the
  same small inline multi-select tag panel** used by the other multi-value categories — not a
  literal on/off switch. The row shows a done/pending visual state once at least one tag is
  proposed for today.
- **D-07:** **Inline-panel categories** (collapsed by default, expand one at a time per
  DAYFORM-04's "in place" wording): grades, sport/coach-rating (per section), reading log, and
  behavior (per D-06).
- **D-08:** **Mood** (5-emoji picker, no coin value, not a coach/grade-style sub-form) is
  **always-expanded directly on its row** — no tap-to-open step, since there's nothing to hide
  behind a panel. Selecting a mood emoji gets a **noticeable selection animation** (bounce/scale/
  glow pop) — more expressive than the other rows' plain state-change feedback, since it carries
  no coin consequence and the user explicitly asked for a "wow" moment here specifically.

### Completion ring
- **D-09:** The ring's denominator is **only categories with something to do for this child
  today** — a category with nothing configured (no sport sections assigned, no behavior tags set
  up by the parent, no extra activities defined) is excluded entirely from both numerator and
  denominator, not counted as permanently incomplete. Mood counts (always applicable, always has
  something to pick). Grades/room/reading count when those blocks are visible per the existing
  `dayBlocksEnabled`/`visibleBlocks` flag-on gating already in `KidDayFillForm.tsx`.

### Re-tapping a done binary row
- **D-10:** Tapping an already-done binary row (room, activity, custom-block) again **toggles it
  back off** — a real on/off switch, freely re-tappable any time before final save/award, exactly
  matching today's accordion checkboxes' existing re-checkable behavior and the sketch's
  `.switch` component. No lock/confirm step.

### Live coin feedback (positive and negative)
- **D-11:** Negative coin deltas (a low grade, a poor coach rating) get **their own floating
  feedback and a real total decrease** — not suppressed, not silently absorbed. Style it
  distinctly from a gain (e.g. red/muted tone, downward drift instead of the existing `floatUp`
  rise) so the mechanic still reads as "a coin event just happened," but visually different in
  valence. The running total (`AnimatedNum`-driven) must genuinely tick down for a loss, not just
  jump to a new value. This matches the product's transparency principle (PROJECT.md: every
  action has a visible, honest consequence — good or bad, never hidden).
- **D-12:** The floating feedback should fire **per category-fill action**, immediately, using
  the existing `sectionCoins` per-category breakdown as the delta source — not only once at final
  save as today. `coinsPreview`/`sectionCoins` (already computed in `KidDayFillForm.tsx`) is the
  right source of truth for per-row deltas; no new coin-calculation logic should be invented,
  only new trigger points into the existing `useCoinAnimation`/`CoinFlyup` mechanism (or a
  same-pattern sibling of it) at each row's interaction handler instead of only at save.

### Reuse vs. rebuild
- **D-13:** Sticky-summary is a **new render/JSX layer over the existing state, validation, save,
  and `/api/wallet/award` logic already in `KidDayFillForm.tsx`** — every `useState` hook,
  `sectionCoins`/`coinsPreview` computation, and the save/award handlers stay as they are. Only
  the accordion JSX (the `CollapsibleRow`-per-section single-open-at-a-time render tree) is
  replaced by the new ring + one-tap-row + inline-panel render tree, selected when
  `fill_style === 'sticky-summary'` (i.e., always, in this phase, per D-01). This follows
  CLAUDE.md's "preserve original code and logic, change only what's necessary." The old
  accordion JSX can be deleted once sticky-summary is the only style actually wired up — it does
  not need to be kept as a dead fallback path.

### Claude's Discretion
- Exact CSS/visual detail of the "loss" floating-feedback treatment beyond "distinct from a
  gain, e.g. red/muted + downward drift" (D-11) — implementer's call, staying within the `K`
  kid-theme palette (e.g. `K.danger` or similar existing muted/warning tone).
- Exact animation curve/scale for the mood row's "wow" selection effect (D-08) — implementer's
  call; should be more pronounced than the other rows' state-change feedback but must still
  respect the app's existing reduced-motion guard pattern (see `05.3-02` STATE.md entry: keyframe
  gated behind a no-preference media query + post-mount JS check).
- Whether the `fill_style` DB column/CHECK-constraint migration is bundled with this phase's
  first plan or split out — no product-level ambiguity here, purely a migration-sequencing call
  matching the existing `backfill_mode` migration's shape (additive, idempotent, `DO $$ ... $$`
  guarded constraint add).
- Precise UI treatment of the Phase-9.3-only `fill_style` control in `ProfileSheet` (D-01) — a
  disabled-looking single confirmed pill, a note, or simply no visible picker at all yet (since
  there's only one real choice) — implementer's call, as long as no dead-end UI for the other two
  styles appears before Phase 9.4.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `sectionCoins` / `coinsPreview` (`KidDayFillForm.tsx`) — already the exact per-category coin
  breakdown needed to drive both the ring's numerator (implicitly) and each row's floating
  feedback delta; no new coin math needed, only new render/trigger wiring
- `ProgressRing`, `AnimatedNum` (`components/kid/design/atoms.tsx`) — ready-made building blocks
  for the sticky ring and ticking total
- `useCoinAnimation` / `CoinFlyup` (`components/kid/CoinAnimation.tsx`) — the existing floating
  "+N" mechanism; needs new call sites (per-row) and a "loss" visual variant (D-11)
- `app/kid/actions/avatar.ts` — copy-paste-adapt template for the new `fill_style` server action

### Established Patterns
- Per-child settings columns follow the `backfill_mode`/`backfill_days` shape: additive
  `ALTER TABLE children ADD COLUMN IF NOT EXISTS` + idempotent CHECK constraint via `DO $$`
- Two distinct "who can change a child setting" patterns already coexist in the codebase: parent-
  gated (`backfill_mode`, via Parent Center `Settings.tsx`) vs. self-serve kid (`avatar_kind`/
  `avatar_config`, via `ProfileSheet.tsx`/`AvatarPicker.tsx`) — `fill_style` follows the
  self-serve pattern (D-03/D-04)
- All child-table writes that aren't plain RLS-writable go through a `'use server'` action using
  `requireFamilyMember()` + `authorizeChildAction()` + the service-role admin client — never a
  direct client-side Supabase `.update()` on `children` for these fields
- Reduced-motion guard pattern (keyframe behind `prefers-reduced-motion` media query + post-mount
  JS check) established in Phase 05.3-02 for the Stamp animation — the new loss-feedback and
  mood "wow" animations (D-11/D-08) should follow the same guard

### Integration Points
- `components/kid/ProfileSheet.tsx` — where the (minimal, per D-01) `fill_style` control gets
  added, alongside the existing avatar-edit entry point
- `app/kid/(app)/day/page.tsx` — mounts `KidDayFillForm`; will need to read the child's
  `fill_style` (defaulting to `sticky-summary`) to select the render layer, though in this phase
  that selection is effectively always `sticky-summary` (D-01)
- `/api/wallet/award` — unchanged; still the sole authoritative coin-crediting call, still fired
  once at final save, independent of the new per-row preview feedback (D-12 is preview/UX only)

<specifics>
## Specific Ideas

- Mood row: the user explicitly asked for a "wow" (заметная анимация при выборе / noticeable
  animation on selection) treatment distinct from the other rows' plainer feedback — see D-08.
- Loss feedback (D-11) should feel like "a coin event happened" but visually read as negative
  (muted/red, downward drift) rather than being hidden or suppressed — explicit transparency
  preference, consistent with PROJECT.md's "every action has a visible, honest consequence."

</specifics>
