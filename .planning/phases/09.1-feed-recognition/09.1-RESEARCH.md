## User Constraints (from CONTEXT.md)

### Locked Decisions

**Money-amount display**
- **D-01:** Strip coin amounts from every rendered card in the redesigned Feed, for every event
  kind — not just reward purchases. This goes beyond the literal text of FEED-03 (which only
  calls out purchases) to match the sketch findings doc's broader validated rule ("no money
  amounts, ever") and the milestone's stated intent (PROJECT.md: "no money or penalty content
  ever shown"). Today `day_filled`, `streak`, `boost`, `reading_approved`, `medal`, `purchase`,
  and `reward_approved` events all set `family_events.amount` and `EventRow` renders it as
  `±N🪙` — that rendering must be removed entirely for the redesigned cards.
- **D-02:** The `amount` column stays in `family_events` and keeps being written by
  `emitFeedEvent` call sites unchanged — it's still useful internally (e.g. for highlight
  ranking, D-03) — only the display layer stops rendering it.
- **D-03 (confirms FEED-04, no new work needed):** No call site currently emits a penalty,
  correction, or negative behavior-tag event to `family_events` — grepped all `emitFeedEvent`
  call sites (award route, shop actions, medal, badge, reading) and none exist for those kinds.
  FEED-04 is satisfied by the absence of such emitters; this phase should NOT add a rail color
  or card treatment for a penalty kind — one should never appear. If a future phase adds such an
  emitter, it must not target `family_events`.

**Story-reel highlight selection**
- **D-04:** Selecting each child's "single biggest highlight" for today uses a fixed priority
  ranking over the day's `family_events` rows for that child (highest wins), not the coin
  amount and not recency. Recommended ranking (most → least significant): `badge` >
  `medal` > `boost` (boost_milestone/weekly_boost) > `streak` (bonus or new record) >
  `reading_approved` > `reward_approved` > `purchase` > `day_filled`. This list is a starting
  point for planning/implementation to refine, not a locked exact ordering — the point is that
  achievement-type events outrank the routine `day_filled` event.
- **D-05:** A child with zero `family_events` rows today gets NO story bubble in the reel (the
  reel simply doesn't include them) — it does not render an empty/placeholder "day not filled
  yet" bubble state.

**Story bubble seen/unseen + tap-through**
- **D-06:** Track per-viewer, per-child, per-day "seen" state in `localStorage`, following the
  existing `feed_seen_${familyId}` key pattern in `lib/repositories/feed.repo.ts` (e.g. a new key
  scoped by `familyId` + `childId` + today's date). This is view-local state, not written to the
  DB — consistent with how whole-feed seen-state already works today.
- **D-07:** Tapping a story bubble opens a full-bleed **modal overlay** (not a new route/page) —
  matching the sketch's "full celebratory moment view." It shows the highlighted event's
  icon/title/body enlarged, then marks that child's story as seen for today (writes the
  localStorage key from D-06).

**Rail color mapping**
- **D-08:** Extend the sketch's 6-category rail-color mapping (boost=mango, medal=berry, day
  completed=mint, reading=grape, purchase=sky, note=neutral) to the remaining real
  `family_events.kind` values:
  - `badge` → berry (same celebration family as medal)
  - `streak` → mango (same momentum/coin-adjacent family as boost)
  - `reward_approved` → sky (fulfillment of a purchase, same as purchase)
  - `level_up` → grape (XP/level color, per `kidTheme.ts` convention)
  - `coins_earned` / `coins_spent` — these enum values exist in the `family_events` CHECK
    constraint and `FeedEventKind` type but have **no current emitter** (grepped, zero call
    sites). Treat as dead/reserved values; no rail color needed unless a future emitter appears.

## Summary

This phase is a **pure client-component redesign** of `components/feed/FamilyFeed.tsx` plus one
new localStorage key convention in `lib/repositories/feed.repo.ts`. No new database migration,
no new server action, no new npm package, and no new `emitFeedEvent` call site are required —
the `family_events` schema and all 11 existing emitter call sites already carry everything the
redesign needs (kind, title, body, icon, amount for internal ranking only, child_id, created_at).

The two genuinely new pieces of logic are: (1) a **pure ranking function** that picks one
"biggest highlight" `FeedEvent` per child from today's events (testable, extractable to its own
module — the codebase has no component-level test infra, only `tests/**/*.test.ts` in a `node`
vitest environment, so pure functions are the only realistically testable unit here), and (2) a
**rail-color lookup table** mapping `FeedEventKind` → one of the six `K` palette semantic colors
(mango/berry/mint/grape/sky/neutral). Everything else — the story bubble modal, the rail visual
itself, and the day-grouping — is a direct visual adaptation of code/patterns that already exist
in this repo (`CollapsibleRow`, `ProfileSheet`/`CelebrationOverlay` full-bleed modal pattern, the
existing `groups` memo).

**Primary recommendation:** Extract the highlight-ranking and rail-color-mapping logic into a
small new pure-TS module (e.g. `lib/kid/feed-highlights.ts`) so it's covered by the existing
`vitest` node-environment test suite; leave `FamilyFeed.tsx`'s data-fetching, realtime
subscription, reactions, and comment-thread code untouched; rewrite only `EventRow`'s markup
(strip the amount span, add the rail) and add a new `StoryReel` + `StoryModal` component pair
above the existing day-grouped list.

### Story Reel Data Source (important precision point)

`FamilyFeed.tsx` already computes `groups` (FamilyFeed.tsx:179-188) as `{ label, items }[]`
ordered newest-first, where `label` is produced by `dayLabel()` (FamilyFeed.tsx:62-70) and is
literally the Russian string `'Сегодня'` for today's events. The story reel's per-child
highlight selection should read from `groups[0].items` **only when** `groups[0].label ===
'Сегодня'` (otherwise there are zero events today → empty reel, matching D-05) — there is no
need for a new Supabase query. Group `groups[0].items` by `child_id`, then apply `pickHighlight`
per child.

**Edge case to flag for the plan (see Open Questions):** `events` is a paginated slice (`PAGE =
30` in `feed.repo.ts:10`, `getFeed`'s default `limit`). In a very active family with many
children and many events, today's events for a given child could theoretically fall outside the
first 30 rows fetched (e.g., 5 kids each generating 7+ events today). This is a pre-existing
characteristic of the component (the day-grouped list already has this limitation) — the phase
is not expected to fix it, but the plan should explicitly decide whether to accept this known
limitation or add a slightly larger initial fetch limit for the story reel specifically.

### Pattern 3: `variant` Prop Coverage

`FamilyFeed` is mounted three times, all requiring the redesign:
- `app/family/feed/page.tsx` → `<FamilyFeed variant="family" />`
- `app/kid/(app)/feed/page.tsx` → `<FamilyFeed variant="kid" hideHeader />`
- `components/parent-center/ParentCenter.tsx:562` and `:648` → `<FamilyFeed variant="parent"/>`
  (mounted twice — once in a nested view, once in the top-level `pcView === 'feed'` branch; both
  render the same component instance shape, no special-casing needed)

The existing `palette(variant)` function (FamilyFeed.tsx:31-47) supplies `ground`/`card`/`ink`/
`accent`/etc. that differ between `kid` (K tokens) and `parent`/`family` (daylight `paper`/`base`
tokens from `lib/design/tokens`). **The new rail colors and story-ring colors should NOT go
through `palette()`** — D-08 defines them as fixed semantic categories sourced directly from `K`
(`kidTheme.ts`) regardless of variant, matching the sketch's intent that "achievement color
coding" is a constant, not a theme-dependent choice. Import `K` directly into `FamilyFeed.tsx`
for this purpose (it's already imported at FamilyFeed.tsx:22 for the kid variant's palette, so
no new import statement is needed — just use `K.mango` etc. unconditionally instead of only
inside the `variant === 'kid'` branch).

### Anti-Patterns to Avoid
- **Don't add a new Supabase query for "today's events per child."** The data is already in the
  `events` state via `getFeed`; querying separately would duplicate realtime-subscription
  complexity and risk drift between the story reel and the card list.
- **Don't route rail/story-ring colors through the variant `palette()` function** — see Pattern 3
  above; this would make the parent/family view's rail colors diverge from the kid view's,
  contradicting the "family bank" cross-surface consistency goal implicit in D-08.
- **Don't reintroduce the sketch's literal placeholder text** (e.g. `"+420 🪙"` in the `STORIES`
  object) into real code — it's illustrative sketch content that pre-dates the D-01 "no money
  amounts anywhere" decision confirmed in this phase's discussion.

## Common Pitfalls

### Pitfall 1: Porting sketch placeholder text verbatim
**What goes wrong:** The canonical sketch source (`sources/001-family-feed/index.html`) contains
illustrative content like `"+420 🪙"` and `"−150 🪙"`-style amounts in its `STORIES` JS object and
in some `.synth-hero .big` text (e.g. `"+420 🪙 недельный буст"` at line ~247 of the D variant
markup) that directly violates D-01 if copied into the real implementation.
**Why it happens:** The sketch was designed before D-01 was locked as "no money amounts, ever
— not just purchases"; the sketch's own internal "content rules" note (in
`references/feed-and-recognition.md`) actually already says "no money amounts, ever" but the
HTML markup itself wasn't fully scrubbed of amounts in headline text.
**How to avoid:** Treat the sketch as a **layout/CSS/interaction** reference only, never copy its
Russian copy text verbatim without checking it against D-01 first.
**Warning signs:** Any headline string in new code containing a `🪙` emoji or a `+`/`−` followed
by digits.

### Pitfall 2: `kind: 'boost'` is a single enum value covering two different award types
**What goes wrong:** D-04's ranking list references `boost (boost_milestone/weekly_boost)` as if
these were distinguishable at the `kind` level. In the real schema and all real emitters
(`app/api/wallet/award/route.ts:792-804`), **both** `weekly_boost` and `boost_milestone` awards
are emitted with the identical `kind: 'boost'`; the only way to tell them apart is by parsing
`ref_id`, which is `${childId}:weekly_boost:${date}` for the weekly boost and
`${childId}:milestone:${sourceId}` for the milestone.
**Why it happens:** `ref_id`/`ref_type` were designed for dedup, not for ranking-time
disambiguation — the CONTEXT.md decision text likely used training/DB-comment knowledge without
re-checking the exact emitter code.
**How to avoid:** If the ranking logic needs to treat "boost_milestone" as more/less significant
than "weekly_boost" specifically (rather than treating all `kind === 'boost'` events equally),
it must parse `ref_id` for the substring `':milestone:'` vs `':weekly_boost:'`. Otherwise, treat
`kind === 'boost'` as one tier in the ranking (simpler, and consistent with D-04's own caveat
that the exact order is "a starting point... not locked").
**Warning signs:** Ranking code that switches on a `boost_milestone` or `weekly_boost` value of
`e.kind` will never match anything (dead branch) since no such kind value exists in the DB CHECK
constraint (`supabase/migrations/2026-09-11-family-feed.sql:18-21`) or the TS type
(`lib/models/feed.types.ts:4-16`).

### Pitfall 3: Rail colors accidentally scoped to `variant === 'kid'` only
**What goes wrong:** Because `K` is currently imported into `FamilyFeed.tsx` specifically to
build the kid-variant branch of `palette()` (FamilyFeed.tsx:32-38), a careless implementation
might gate the new rail-color lookup behind `variant === 'kid'` and fall back to some daylight
color for `parent`/`family` variants, producing inconsistent rail colors across surfaces.
**Why it happens:** Following the existing `palette()` branching pattern too literally.
**How to avoid:** Define `RAIL_COLOR_MAP` as a standalone `Record<FeedEventKind, string>` built
from `K.*` constants and use it unconditionally in `EventRow`, independent of `variant`/`C`.
**Warning signs:** Rail color changes when switching from `/kid/feed` to `/family/feed` for the
same underlying event.

### Pitfall 4: Sticky day-label header offset breaks once a story reel is added above it
**What goes wrong:** The existing sticky day-label divider uses `top: hideHeader ? 65 : 0`
(FamilyFeed.tsx:239) to sit just below the kid screen's sticky header. Once a story reel is
inserted between the header and the day-grouped list, that hardcoded `65`/`0` offset will likely
need to account for the story reel's height too, or the reel itself needs to also be sticky /
scroll away before the day labels take over.
**Why it happens:** The offset was tuned for the current layout (header + card list only); the
story reel is new vertical space above the list.
**How to avoid:** Explicitly decide (in the plan) whether the story reel scrolls away normally
(simplest — matches the sketch, which does not make the reel sticky) or needs its own sticky
behavior; if it scrolls away normally, the existing `top: hideHeader ? 65 : 0` sticky offset for
day labels does NOT need to change (it will just kick in slightly later during scroll, once the
reel has scrolled past).
**Warning signs:** Day-label headers visually overlapping the story reel, or a gap/jump when the
list re-renders after the reel mounts.

### Pitfall 5: Reusing the same "seen" key namespace between whole-feed and per-story tracking
**What goes wrong:** `feed.repo.ts`'s existing key is `feed_seen_${familyId}` (line 142). A new
per-child-per-day key must not collide with this (e.g. `feed_seen_${familyId}_${childId}_${date}`
is safe since it's a strict superstring, but a careless naming like `feed_seen_${familyId}:${childId}`
using different separators for different features increases the chance of a future maintenance
bug parsing these keys).
**How to avoid:** Adopt one explicit, documented key format for the new per-child story-seen
state, e.g. `feed_story_seen_${familyId}_${childId}_${date}` (distinct prefix `feed_story_seen_`
vs the existing `feed_seen_`), and add it as a sibling export in `feed.repo.ts` right next to

## Open Questions

1. **Should `kind === 'boost'` be split into "milestone" vs "weekly" tiers for D-04 ranking?**
   - What we know: The DB schema and every real emitter only ever write `kind: 'boost'`; the
     distinction lives only in `ref_id`'s embedded substring (`milestone` vs `weekly_boost`).
   - What's unclear: Whether the user's mental model (from D-04's context, which spells out
     "boost (boost_milestone/weekly_boost)") requires them to actually rank differently within
     the `boost` kind, or whether that parenthetical was just explaining *what a boost event is*.
   - Recommendation: Default to treating all `boost` events as one rank tier (simplest, matches
     D-04's own "starting point, not locked" caveat); only add `ref_id` parsing if a
     `checkpoint:human-verify` or later discussion surfaces a concrete case where it matters.

2. **Does the story reel need a larger initial fetch limit than the day-list's `PAGE = 30`?**
   - What we know: `getFeed`'s default limit is 30 rows total across the whole family
     (`feed.repo.ts:10,21`); a busy family with 3+ children could plausibly generate more than 30
     events across all kinds before a story-reel-relevant highlight for a later-alphabetical
     child appears in the fetched slice.
   - What's unclear: Whether this is a real risk for this app's actual family sizes (per
     `CLAUDE.md`, the schema is "multi-family," but the concrete families in use today are small,
     e.g. 2 kids per the legacy Adam/Alim example).
   - Recommendation: Ship without a special-cased larger fetch for the story reel (reuse the
     existing 30-row fetch); note it as a known limitation rather than pre-optimizing for an
     unconfirmed scale requirement.
