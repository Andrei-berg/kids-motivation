# Phase 9.1: feed-recognition - Context

**Gathered:** 2026-09-17
**Status:** Ready for planning

<domain>
## Phase Boundary

Reframe the existing Family Feed (`components/feed/FamilyFeed.tsx` + `family_events` schema)
from a flat activity/transaction log into a motivational recognition stream:

1. A story-reel of per-child "today's biggest highlight" bubbles at the top
2. Below it, the existing day-grouped event list restyled as hero-stat cards with a
   color-coded left rail (reusing the real `CollapsibleRow` rail pattern)
3. Removing all money/coin-amount display and guaranteeing no penalty/correction/negative
   behavior-tag event ever renders

This phase does NOT add reactions, the "подколоть" tease mechanic, or kid→kid medals as a new
feed event type — those are FEED-05/06/07, scoped to Phase 9.2 (feed-social). Reactions/comments
already exist in the current component and continue to work unchanged; only the story reel,
card visual design, and money/penalty content rules are in scope here.

</domain>

<decisions>
## Implementation Decisions

### Money-amount display
- **D-01:** Strip coin amounts from every rendered card in the redesigned Feed, for every event
  kind — not just reward purchases. This goes beyond the literal text of FEED-03 (which only
  calls out purchases) to match the sketch findings doc's broader validated rule ("no money
  amounts, ever") and the milestone's stated intent (PROJECT.md: "no money or penalty content
  ever shown"). Today `day_filled`, `streak`, `boost`, `reading_approved`, `medal`, `purchase`,
  and `reward_approved` events all set `family_events.amount` and `EventRow` renders it as
  `±N🪙` — that rendering must be removed entirely for the redesigned cards.
- **D-02:** The `amount` column stays in `family_events` and keeps being written by
  `emitFeedEvent` call sites unchanged — it's still useful internally (e.g. for highlight
  ranking, D-03) — only the display layer stops rendering it.
- **D-03 (confirms FEED-04, no new work needed):** No call site currently emits a penalty,
  correction, or negative behavior-tag event to `family_events` — grepped all `emitFeedEvent`
  call sites (award route, shop actions, medal, badge, reading) and none exist for those kinds.
  FEED-04 is satisfied by the absence of such emitters; this phase should NOT add a rail color
  or card treatment for a penalty kind — one should never appear. If a future phase adds such an
  emitter, it must not target `family_events`.

### Story-reel highlight selection
- **D-04:** Selecting each child's "single biggest highlight" for today uses a fixed priority
  ranking over the day's `family_events` rows for that child (highest wins), not the coin
  amount and not recency. Recommended ranking (most → least significant): `badge` >
  `medal` > `boost` (boost_milestone/weekly_boost) > `streak` (bonus or new record) >
  `reading_approved` > `reward_approved` > `purchase` > `day_filled`. This list is a starting
  point for planning/implementation to refine, not a locked exact ordering — the point is that
  achievement-type events outrank the routine `day_filled` event.
- **D-05:** A child with zero `family_events` rows today gets NO story bubble in the reel (the
  reel simply doesn't include them) — it does not render an empty/placeholder "day not filled
  yet" bubble state.

### Story bubble seen/unseen + tap-through
- **D-06:** Track per-viewer, per-child, per-day "seen" state in `localStorage`, following the
  existing `feed_seen_${familyId}` key pattern in `lib/repositories/feed.repo.ts` (e.g. a new key
  scoped by `familyId` + `childId` + today's date). This is view-local state, not written to the
  DB — consistent with how whole-feed seen-state already works today.
- **D-07:** Tapping a story bubble opens a full-bleed **modal overlay** (not a new route/page) —
  matching the sketch's "full celebratory moment view." It shows the highlighted event's
  icon/title/body enlarged, then marks that child's story as seen for today (writes the
  localStorage key from D-06).

### Rail color mapping
- **D-08:** Extend the sketch's 6-category rail-color mapping (boost=mango, medal=berry, day
  completed=mint, reading=grape, purchase=sky, note=neutral) to the remaining real
  `family_events.kind` values:
  - `badge` → berry (same celebration family as medal)
  - `streak` → mango (same momentum/coin-adjacent family as boost)
  - `reward_approved` → sky (fulfillment of a purchase, same as purchase)
  - `level_up` → grape (XP/level color, per `kidTheme.ts` convention)
  - `coins_earned` / `coins_spent` — these enum values exist in the `family_events` CHECK
    constraint and `FeedEventKind` type but have **no current emitter** (grepped, zero call
    sites). Treat as dead/reserved values; no rail color needed unless a future emitter appears.

### Claude's Discretion
- Exact visual treatment of the modal overlay (animation, dismiss gesture) beyond "full-bleed,
  shows icon/title/body large" — follow the sketch's variant D HTML/CSS as the base.
- Whether/how the composer (free-text note box, parent/extended only) and existing
  reactions/comments UI get restyled to match the new card visual language — they must keep
  working, exact pixel treatment is an implementation call.
- Final exact priority order within D-04's ranking list if evidence during implementation
  suggests reordering two adjacent kinds.

</decisions>

## Existing Code Insights

### Reusable Assets
- `components/kid/design/atoms.tsx` `CollapsibleRow` — the exact left-rail visual pattern to
  reuse for `.synth-rail` (a 5px `borderRadius: '0 4px 4px 0'` bar, colored by state/category)
- `components/kid/design/kidTheme.ts` (`K`) — sky/grape/mint/mango/berry palette, already used
  throughout `FamilyFeed.tsx`'s kid variant
- `lib/repositories/children.repo.ts` `getChildren()` — already used in `FamilyFeed.tsx` to
  resolve `child.emoji`/name/accent color per event; same source for story-reel avatars
- Existing reactions (`QUICK_EMOJI`, `toggleReaction`, optimistic update) and comment thread
  (`CommentThread`) — fully built, keep working, just needs restyling to match new cards

### Established Patterns
- `emitFeedEvent`'s `mode: 'once' | 'bump'` dedup on `(family_id, kind, ref_type, ref_id)` — any
  new emit call added in this phase (if any) must follow this convention
- Money mutations are server-side only / `family_events` writes go through the service-role
  `admin` client inside server actions or API routes (`app/api/wallet/award/route.ts`,
  `app/actions/*.ts`) — this phase is UI-only (no new money logic) so no new privileged writes
  are expected, but if highlight-ranking logic needs a server helper, it must not touch money
  tables directly
- `FamilyFeed` variant prop (`'parent' | 'kid' | 'family'`) picks palette + composer visibility;
  the redesign applies to all three variants (mounted at `app/family/feed/page.tsx` and
  `app/kid/(app)/feed/page.tsx`)

### Integration Points
- `app/kid/(app)/feed/page.tsx` calls `markFeedSeen(familyId)` on an interval and on mount —
  the new per-child story-seen tracking (D-06) is additive to this, not a replacement
- `wallet_settings.feed_enabled` / `feed_visible_to_kids` already gate whether the kid can see
  the feed at all — unaffected by this phase
