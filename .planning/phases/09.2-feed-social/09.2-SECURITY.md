## Escalation: T-092-17 / CR-01 — `family_event_reactions` INSERT policy missing ownership check

**Finding confirmed independently**, not merely re-stated from 09.2-REVIEW.md. Reading
`supabase/migrations/2026-09-11-family-feed.sql:95-99` directly:

```sql
CREATE POLICY "Family members add event reactions" ON family_event_reactions
  FOR INSERT WITH CHECK (
    family_id IN (SELECT family_id FROM family_members WHERE user_id = auth.uid())
  );
```

versus the sibling `family_event_comments` INSERT policy (same migration, lines 131-136):

```sql
CREATE POLICY "Family members add event comments" ON family_event_comments
  FOR INSERT WITH CHECK (
    family_id IN (SELECT family_id FROM family_members WHERE user_id = auth.uid())
    AND author_member_id IN (SELECT id::text FROM family_members WHERE user_id = auth.uid())
  );
```

The reactions policy has no equivalent `AND member_id IN (...)` clause. The DELETE
policy on the same table gets it right (`member_id IN (SELECT id::text FROM
family_members WHERE user_id = auth.uid())`) — only INSERT is missing it. No CHECK
constraint, trigger, or server-side enforcement fills this gap; `addReaction()`
(`lib/repositories/feed.repo.ts:63-71`) writes a caller-supplied `member_id`
straight through on the RLS-bound anon client.

**Why this resolves T-092-17 as OPEN, not CLOSED:** the plan's stated mitigation —
"the reactions RLS policy pins it to the caller's own `family_members` row" — does
not match the deployed policy. `FamilyFeed.tsx` always happening to pass `me.id` is
a well-behaved-client convention, not a boundary; any authenticated family member
(including a child) can call `supabase.from('family_event_reactions').insert(...)`
directly from the browser console with another member's `member_id` and forge that
member's reaction (e.g. forge a parent's ❤️, or manipulate the `mine` state
`summarizeReactions` shows to other viewers).

**Why this is escalated rather than filed as a plain OPEN_THREATS line item:**

1. The vulnerable policy was authored in Phase 9.1 (`2026-09-11-family-feed.sql`),
   not introduced by any 09.2 plan — 09.2 only *widened the picker* to the existing
   emoji set (T-092-16) and *extended* `feed.repo.ts`'s file list, it did not create
   the flawed policy.
2. The same pattern flaw was flagged as already present in `chat_reactions` (per
   09.2-REVIEW.md CR-01) — this is a repeated pattern across two tables, not a
   one-off, so the fix decision affects more than this phase's file list.
3. Fixing it requires a new migration (`ALTER`/`DROP+CREATE POLICY`) to prod, which
   this agent is not authorized to write or apply (implementation files are
   read-only for this audit).
4. The phase's own verification (09.2-VERIFICATION.md) already made a judgment call
   to not block the phase's *goal* on this — a reasonable call for goal-verification,
   but that does not make the threat register's own claimed mitigation true, and a
   security audit answers a different question ("is the declared mitigation
   present") than a goal audit ("does the feature work for a well-behaved client").

**Resolution:** Operator chose to apply the fix immediately rather than accept
as tracked risk. `supabase/migrations/2026-09-19-reaction-insert-ownership.sql`
was written, applied to prod via the project's standard `pg` connection process,
and independently re-verified against `pg_policies` (both policies now show the
`AND member_id IN (...)` clause in `with_check`). `chat_reactions`' identical
gap (flagged in 09.2-REVIEW.md as likely present) was confirmed by direct read
of `supabase-schema-chat-reactions.sql` and fixed in the same migration.
Full toolchain (`tsc`, `npm test`) re-run clean after the fix — no application
code changes were needed since `FamilyFeed.tsx` already always sends the
caller's own `member_id`.
