# Phase 9.2: feed-social - Context

**Gathered:** 2026-09-18
**Status:** Ready for planning

<domain>
## Phase Boundary

Add three social-interaction primitives to the Family Feed (`components/feed/FamilyFeed.tsx`,
restyled in Phase 9.1) so family members can recognize and playfully needle each other directly
on feed cards:

1. **Reactions (FEED-05)** — already fully implemented server-side and in the UI; this phase
   closes a small gap (picker only exposes 4 of 6 allowed emoji) and adds a polish detail (pop
   animation).
2. **"Подколоть" tease (FEED-06)** — new: a button on any feed card reveals a tray of
   pre-written playful phrases; picking one posts a reply bubble under the card.
3. **Kid→kid medal (FEED-07)** — new: extend the existing parent-only "medal of the day" flow so
   a child can also send a medal to a sibling, rendering as its own recognized event distinct
   from a parent-sent medal.

Out of scope: the story reel, card visual redesign, and money/penalty display rules — already
done in Phase 9.1. Comments (the existing `CommentThread`) are untouched except for how tease
replies render alongside them.

</domain>

<decisions>
## Implementation Decisions

### Reactions — closing FEED-05
- **D-01:** Expand the reaction picker from the current hardcoded `QUICK_EMOJI` (4: ❤️👍🔥🏆) to
  all 6 emoji already allowed by the `family_event_reactions.emoji` CHECK constraint and by
  `FEED_REACTION_EMOJI` in `lib/models/feed.types.ts`: ❤️ 👍 🔥 🏆 😂 🎉. No DB/schema change —
  purely a UI change in `components/feed/FamilyFeed.tsx`.
- **D-02:** Add a "pop" tap animation on the reaction chip when its state changes (lit/unlit),
  per the sketch's `.reaction-chip.pop` keyframe (`transform: scale(1.28)` at 40%, 0.35s ease).
  Current code has no animation on state change.
- **D-03:** Reactions stay silent — no push notification when someone reacts to a card. The
  visible count + pop animation is sufficient feedback. Do not add a new `notifyChild`/
  `notifyParent` call site for reactions.
- No other changes to reactions — targeting (any family member, any card), storage
  (`family_event_reactions`), and toggle behavior (`addReaction`/`removeReaction`) are already
  correct and complete; this phase does not touch `lib/repositories/feed.repo.ts` reaction
  functions.

### "Подколоть" (tease) — phrase set
- **D-04:** Locked list of 17 phrases, grouped by event kind (not one universal list):
  - **Achievement group** — applies to `badge`, `medal`, `streak`, `boost`, `level_up` cards:
    «Красавчик 🔥» / «Погнали на рекорд!» / «Ну ты и мастер! 😎» / «Вот это да, снимаю шляпу 🎩»
    / «Теперь моя очередь удивлять 😏» / «Держись, я догоняю! 💪»
  - **Routine group** — applies to `day_filled`, `reading_approved` cards:
    «Ну погоди 😤» / «Не забудь про уроки 😤» / «Я быстрее наберу 😏» / «Ты так не сможешь
    завтра 😏» / «Завтра я тебя обгоню 🏃» / «Скромно, но пойдёт 😏»
  - **Purchase/reward group** — applies to `purchase`, `reward_approved` cards:
    «Всё промотал? 😂» / «Приятной покупки, транжира 💸» / «А мне не завидно… ну ладно, немного
    😏» / «Копи-копи, а потом раз — и нету 😂» / «Богач нашёлся 👑»
  - Cards for other kinds not covered above (`coins_earned`, `coins_spent`, `note`) fall back to
    the **Routine group** (Claude's discretion on exact fallback, but must not leave the tease
    button with an empty tray).

### "Подколоть" — mechanics
- **D-05:** Any family member can tease any card — not restricted to kid→sibling despite the
  literal FEED-06 wording ("a child can send a sibling a tease"). This is a deliberate broadening
  confirmed by the user: parents/extended members can also tease, and a card of any kind
  (including a parent's free-text note) can receive a tease. The only thing still blocked: a
  person cannot tease their own card (the tease button/tray should not appear on your own event,
  same principle as not reacting-to-self is NOT restricted — but tease specifically is, since
  self-teasing makes no sense as a "reply").
- **D-06:** Storage/rendering — reuse the existing comment infrastructure
  (`family_event_comments` table + `CommentThread` UI in `FamilyFeed.tsx`) rather than building a
  new table. Insert a tease as a comment row tagged so it renders distinctly (e.g. a
  `metadata`/type marker or a reserved body-prefix convention — implementer's call) as a small
  reply bubble matching the sketch's `.tease-reply` style, not as a plain comment. User explicitly
  deferred this technical choice to Claude ("как лучше сам выбирай" — whatever's best); the
  recommended approach (reuse + tag) is locked because it needs no new RLS policy, realtime
  subscription, or thread-rendering logic — it rides on what `CommentThread` already does.
- **D-07:** Rate limit: one tease per (person, card) — mirrors how one reaction-per-emoji-per-
  person-per-event already works. A second tap on the tease button for a card the same person
  already teased should not create a duplicate reply (implementer's call whether that means a
  toggle/removal, a disabled tray, or a friendly "already teased" state — pick whichever is
  simplest given the reused comment storage).

### Kid→kid medal — economy & targeting
- **D-08:** A kid-sent medal carries **zero coins** — no minting, no transfer. This is a
  deliberate economy-safety decision: kids must not have a path to create or move real coin
  balance to each other outside the existing, audited p2p_transfers flow. `sendMedal`'s existing
  parent path keeps crediting coins as today (unchanged); only the new kid-initiated path is
  coins=0.
- **D-09:** Daily cap is **separate per sender role** — a child can receive one parent-sent medal
  AND one kid-sent medal on the same day (two independent caps), not sharing the existing
  `medals` table's implicit one-row-per-child-per-day pattern. Requires either a composite
  uniqueness check that includes sender-type, or a parallel mechanism for kid-sent medals (e.g. a
  `sent_by_role` or `sender_member_id` column feeding the per-day lookup) — implementer's call on
  exact schema shape, but the *behavior* (independent caps) is locked.
- **D-10:** Sender-side limit: a kid can send **at most one medal per day total** (to one sibling
  target). Not per-recipient — if a family has 3+ kids, a sender who already sent today's medal
  to sibling A cannot also send one to sibling B same day.
- **D-11:** Kid's medal message is **not freeform** — picked from a fixed locked set of 8
  phrases, consistent with the project's kids-don't-get-freeform-text-fields pattern (mirrors
  D-04's tease phrases):
  «Ты сегодня молодец 🏅» / «Горжусь тобой! 🌟» / «Красавчик, так держать! 💪» / «Ты крут,
  признаю 🔥» / «Заслуженно! 🏆» / «Ты меня вдохновляешь сегодня ✨» / «Респект! 🙌» / «Лучший
  день, продолжай в том же духе 🚀»
  (Parent's existing freeform 200-char message field is unchanged — this fixed set applies only
  to the new kid-initiated send path.)
- **D-12:** The feed card must distinguish sender: a kid-sent medal shows "Медаль от {sibling
  display name} 🏅" (or equivalent), while a parent-sent medal keeps today's "Медаль дня 🏅".
  This likely means passing/reading `actorMemberId` (already a column on `family_events`, but
  `sendMedal` doesn't currently set it) or a `metadata.senderRole`/`metadata.senderName` field so
  the feed card render function can tell the two apart. FEED-07 already gets "its own recognized
  event type" for free (both already emit `kind: 'medal'` to `family_events`) — the remaining
  work for FEED-07 is (a) allowing a *child* to trigger the send at all (new/adapted server
  action with a child-appropriate auth guard, not `requireParent()`), and (b) this sender-copy
  distinction.

### Claude's Discretion
- Exact fallback tease-phrase group for event kinds not explicitly grouped (`coins_earned`,
  `coins_spent`, `note`) — use the Routine group.
- Exact technical shape of the "tag a comment as a tease" marker (metadata field vs. reserved
  convention) and of the "separate daily cap per sender role" schema change (new column vs.
  derived check) — pick whichever fits the existing `medals`/comments schema with the least
  disruption, per D-06 and D-09.
- Whether re-tapping an already-sent tease toggles it off or shows a disabled/confirmed state
  (D-07) — implementer's call.
- Exact auth guard shape for the new kid-initiated medal-send server action (e.g. a
  `requireFamilyMember` + explicit role check vs. a new guard helper) — must still run
  server-side with the service-role client per CLAUDE.md's money-mutation rule (medals write to
  `wallet`-adjacent flows even at coins=0, since it touches the `medals` table and `family_events`).

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `CommentThread` (in `FamilyFeed.tsx`) + `family_event_comments` — the thread UI and storage to
  reuse for tease replies (D-06)
- `p2p_transfers` infra (money/security model, `lib/repositories/wallet.repo.ts`) — considered
  and explicitly rejected for kid-sent medals (D-08 chose zero-coins instead); relevant only if a
  future phase revisits "kid spends own coins to fund a medal"
- `lib/supabase/admin.ts` guards (`requireParent`, `requireFamilyMember`, `assertChildInFamily`)
  — building blocks for the new kid-initiated medal auth guard

### Established Patterns
- `emitFeedEvent`'s `mode: 'once' | 'bump'` dedup on `(family_id, kind, ref_type, ref_id)` —
  any new medal/tease-related emit call must follow this convention
- Money mutations are server-side only, service-role client, behind an auth guard (CLAUDE.md) —
  the kid-initiated medal-send action must follow this even at coins=0, because it still writes
  to the `medals` table and could be extended later
- Reactions already establish the "any family member reacts freely, one active state per
  (person, emoji, event)" pattern — tease's one-per-(person, card) rate limit (D-07) mirrors it

### Integration Points
- `app/kid/(app)/feed/page.tsx` and `app/family/feed/page.tsx` mount `FamilyFeed` — both need the
  tease button/tray and (for the kid variant) a medal-send entry point
- `notifyChild`/`notifyParent` (push dispatchers) — NOT used for reactions (D-03) or specified
  for tease/medal in this discussion; if a push feels warranted for tease/medal receipt,
  implementer should follow the existing medal push pattern in `send-medal.ts` (`notifyChild`
  call) for consistency, but this wasn't explicitly locked — treat as discretion, default to
  matching what parent-sent medals already do (they do push)
