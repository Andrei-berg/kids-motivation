Add a `describe('guards and caps')` block with one `it` per case. Every rejection case must
assert **both** `success === false` **and** that no `medals` row was written (count by
`family_id` for the day stays at its pre-call value) — a guard that returns an error *after*
inserting would otherwise pass.

1. **Off-list phrase (D-11).** `sendKidMedal({ targetChildId: recipientA, phrase: 'Держи 1000 монет' })`
   → `error === 'Недопустимое сообщение'`, zero rows.
2. **Self-send.** Target the sender's own child id → `success === false`, zero rows. Assert the
   error is non-empty; do not assert its exact wording beyond it being the self-send message.
3. **Non-child caller.** `mockRequireFamilyMember` resolves with `role: 'parent', childId: null`
   → `success === false`, zero rows. This proves `sendKidMedal` is not a second, weaker parent
   endpoint (parents keep `sendMedal`).
4. **Cross-family target.** Target the outsider family's child id while authenticated as the
   sender → `success === false`, and assert zero `medals` rows exist for that outsider child.
   This is the key authorization test: the action derives the family from the session, so a
   valid-looking `targetChildId` from elsewhere must not resolve.
5. **Sender cap is per-day-total (D-10).** Send successfully to recipient A, then send to
   recipient **B** with a different phrase → second call returns
   `error === 'Ты уже отправил медаль сегодня'`, and B has zero medal rows. (This is the case a
   naive per-recipient cap would let through.)
6. **Recipient cap is per-sender-role (D-09).** With the service client, insert a parent-style
   row directly — `{ family_id, child_id: recipientA, date: today, message: 'Медаль дня', coins: 0, sender_role: 'parent' }`
   — then run a kid send to recipient A. It must **succeed**, and `medals` for
   `(recipientA, today)` must then hold exactly 2 rows, one per `sender_role`. Insert the parent
   row directly rather than calling `sendMedal` so this test does not depend on a parent session
   or touch the wallet credit path.
7. **Duplicate kid medal for the same recipient (D-09, other direction).** After a successful
   kid send to recipient A, a *second* kid send to A (use a fresh `senderMemberId`? no — reuse
   the same sender, whose sender cap fires first) is already covered by case 5; instead assert
   the DB-level guarantee directly: a second raw insert of
   `{ family_id, child_id: recipientA, date: today, sender_role: 'child', sender_member_id: senderMemberId, message: MEDAL_PHRASES[1], coins: 0 }`
   via the service client fails with Postgres error code `23505` (unique violation on
   `medals_recipient_day_role` / `medals_kid_sender_day`). This proves the caps survive a race
   that slips past the app-level read checks.

Keep the `afterEach` medals/`family_events` cleanup from Task 1 authoritative — each case starts
from an empty day.
