# Phase 09.2: Code Review Report

**Reviewed:** 2026-09-19
**Depth:** standard
**Files Reviewed:** 13
**Status:** issues_found

## Summary

Reviewed the FEED-05/06/07 additions (emoji reactions, "Подколоть" tease replies,
kid-to-kid zero-coin medals). The kid-medal path itself is well-guarded: coins are
hardcoded to `0` and never accepted from the client, the phrase is validated
server-side against a locked allow-list, family/self/role checks run before any
write, and the new `medals` daily-cap logic is correctly backstopped by Postgres
unique indexes (verified against `tests/integration/kid-medal.test.ts`, including
a real 23505-race test). No money table (`wallet`, `wallet_transactions`, etc.) is
touched anywhere in the kid-medal flow — confirmed by both static reading and the
"moves no coins and writes no wallet transaction" integration test. `send-medal.ts`'s
diff for this phase is a single `sender_role='parent'` addition; its pre-existing
non-fatal coin-credit-failure behavior is unchanged and out of this phase's scope.

The one **critical** finding is not new to this phase's diff, but it is directly
exploitable through code delivered/extended in this phase's file list
(`lib/repositories/feed.repo.ts`'s `addReaction`): the `family_event_reactions`
table's INSERT row-level-security policy never checks that the caller owns the
`member_id` they're writing, unlike the sibling `family_event_comments` policy
which does. Any authenticated family member can spoof a reaction as any other
member of the same family. Given FEED-05's whole purpose this phase was building
trustworthy "who reacted" UI (the pop animation, the `mine` highlight state), this
gap undermines the feature's integrity guarantee and is flagged as a blocker.

Remaining findings are edge-case robustness gaps in the new kid-medal cap logic,
an unguarded optimistic-UI path for reactions, and a couple of minor
maintainability nits in the composer/action files.

## Critical Issues

### CR-01: `family_event_reactions` INSERT policy allows spoofing another member's reaction

**File:** `lib/repositories/feed.repo.ts:63-71` (exploits `supabase/migrations/2026-09-11-family-feed.sql:94-98`)

**Issue:** `addReaction()` accepts a caller-supplied `memberId` and writes it directly:

```ts
export async function addReaction(params: { eventId: string; familyId: string; memberId: string; emoji: string }): Promise<void> {
  const { error } = await supabase
    .from('family_event_reactions')
    .upsert([{ event_id: params.eventId, family_id: params.familyId, member_id: params.memberId, emoji: params.emoji }], ...)
```

The UI (`FamilyFeed.tsx`'s `toggleReaction`) always passes `me.id`, but this is a
client-writable table protected only by RLS (per this codebase's own security
model: "RLS is the security boundary"). The actual INSERT policy is:

```sql
CREATE POLICY "Family members add event reactions" ON family_event_reactions
  FOR INSERT WITH CHECK (
    family_id IN (SELECT family_id FROM family_members WHERE user_id = auth.uid())
  );
```

This checks only that the caller belongs to `family_id` — it never checks that
`member_id` is the caller's own `family_members.id`. Compare to the sibling
`family_event_comments` INSERT policy added in the same migration, which
correctly adds `AND author_member_id IN (SELECT id::text FROM family_members
WHERE user_id = auth.uid())`. The DELETE policy on reactions gets this right too
(`member_id IN (SELECT id::text FROM family_members WHERE user_id = auth.uid())`)
— only INSERT is missing the check.

Any authenticated family member (including a child) can open the browser console
and call `supabase.from('family_event_reactions').insert({event_id, family_id:
<own family>, member_id: <any other member's id>, emoji})` to fake another
person's reaction — e.g. forging a parent's "❤️" on their own card, or forging a
sibling's reaction to manipulate the `mine` state other viewers see
(`summarizeReactions`). This same flaw was already present in the `chat_reactions`
policy this table intentionally mirrors, so it is not newly introduced by 09.2,
but it is directly reachable through `feed.repo.ts` as delivered in this phase's
file list and directly undermines the reaction feature's trust model.

**Fix:** Patch the INSERT policy (new migration) to match the comments policy:

```sql
DROP POLICY IF EXISTS "Family members add event reactions" ON family_event_reactions;
CREATE POLICY "Family members add event reactions" ON family_event_reactions
  FOR INSERT WITH CHECK (
    family_id IN (SELECT family_id FROM family_members WHERE user_id = auth.uid())
    AND member_id IN (SELECT id::text FROM family_members WHERE user_id = auth.uid())
  );
```

Consider auditing `chat_reactions` for the identical gap while in this area.

## Warnings

### WR-01: D-10 sender cap can silently no-op when `sender_member_id` resolves to `null`

**File:** `app/actions/send-kid-medal.ts:72-102`

**Issue:** `senderMemberId` is derived from a second, independent lookup of
`family_members` by `user_id` (not reused from `requireFamilyMember()`'s result):

```ts
const { data: senderMember } = await admin.from('family_members').select('id, display_name').eq('user_id', member.userId).maybeSingle()
const senderMemberId = senderMember?.id ?? null
...
const { data: senderCapHit } = await admin.from('medals').select('id')
  .eq('sender_member_id', senderMemberId)
  .eq('date', today)
  .eq('sender_role', 'child')
  .maybeSingle()
```

If this lookup ever returns no row (or `.maybeSingle()` errors because more than
one row matches `user_id`), `senderMemberId` is `null`, and the cap check becomes
`.eq('sender_member_id', null)`. Supabase-js's own filter builder recommends
`.is(column, null)` for null comparisons — `.eq()` serializes to
`sender_member_id=eq.null`, which does not reliably match `IS NULL` semantics in
Postgres (the codebase itself uses `.is('child_id', null)` / `.is('verified',
null)` elsewhere for exactly this reason — see `lib/repositories/day-blocks.repo.ts:30`
and `lib/vacation-api.ts:125`). The app-level cap check would then find no
existing row and let the send proceed. The DB-level backstop
(`medals_kid_sender_day` — a **partial** unique index on
`(sender_member_id, date) WHERE sender_role='child'`) also would not catch a
repeat, because Postgres unique indexes treat every `NULL` as distinct — multiple
`NULL` `sender_member_id` rows are all allowed. In that (admittedly narrow) state,
D-10's "one kid-sent medal per sender per day" cap is unenforced both in the app
and in the DB.

**Fix:** Reuse the id already available and fail closed instead of silently
falling back to `null`:

```ts
if (!senderMember?.id) {
  return { success: false, error: 'Профиль ребёнка не найден' }
}
const senderMemberId = senderMember.id
```

And/or use `.is('sender_member_id', null)` if a null-sender code path is ever
intentionally retained.

### WR-02: Cap-check reads ignore query errors

**File:** `app/actions/send-kid-medal.ts:93-116`

**Issue:** Both cap-check selects destructure only `data`, discarding `error`:

```ts
const { data: senderCapHit } = await admin.from('medals').select('id')...maybeSingle()
...
const { data: recipientCapHit } = await admin.from('medals').select('id')...maybeSingle()
```

A transient DB error on either read is silently treated as "no cap hit," and the
code proceeds to the insert. This is backstopped by the unique indexes (so it
won't double-write), but it is inconsistent with the rest of the codebase's
pattern of logging read errors (see `feed.repo.ts`, which logs every
`console.error(...)` on a failed read) and makes failures invisible in
production logs.

**Fix:**

```ts
const { data: senderCapHit, error: senderCapErr } = await admin...
if (senderCapErr) console.error('[sendKidMedal] sender cap check failed:', senderCapErr)
```

### WR-03: Optimistic reaction toggle has no failure rollback

**File:** `components/feed/FamilyFeed.tsx:182-197`

**Issue:** `toggleReaction` updates local state immediately, then fires
`addReaction`/`removeReaction` without checking success:

```ts
async function toggleReaction(eventId: string, emoji: string) {
  ...
  setReactions(prev => { ... }) // optimistic
  if (mine) await removeReaction({ eventId, memberId: me.id, emoji })
  else await addReaction({ eventId, familyId, memberId: me.id, emoji })
}
```

Both `addReaction`/`removeReaction` in `feed.repo.ts` swallow their own errors
(`console.error` only, no thrown/returned failure signal), so there is no way for
`toggleReaction` to detect a failed write and revert the optimistic state. On a
flaky network or an RLS rejection, the chip will show the wrong state
(reacted/not-reacted) until the next full reload or realtime event resync.

**Fix:** Have `addReaction`/`removeReaction` return a boolean/result, and revert
the optimistic `setReactions` update on failure:

```ts
const ok = mine ? await removeReaction(...) : await addReaction(...)
if (!ok) setReactions(prev => { /* revert */ })
```

### WR-04: `MedalComposer` branches on an exact server error string

**File:** `components/feed/MedalComposer.tsx:47-51`

**Issue:**

```ts
if (res.error === 'Ты уже отправил медаль сегодня') {
  setCapped(true)
} else {
  setError(res.error ?? 'Не получилось отправить')
}
```

The "already sent today" UI branch is selected by exact string equality against
the Russian copy defined in `app/actions/send-kid-medal.ts`. Any future wording
tweak to that message (translation, copy edit, punctuation change) silently
breaks this branch — it will fall through to the generic error UI instead of the
dedicated "capped" screen, with no compiler or test signal (no test in
`tests/integration/kid-medal.test.ts` asserts on the composer's branching, only
on the raw action's returned string).

**Fix:** Return a structured error code from `sendKidMedal` (e.g. `{ success:
false, code: 'SENDER_CAPPED', error: '...' }`) and branch on `code` instead of
the localized message.

### WR-05: Unexpected `sendKidMedal` failures are unhandled in the composer

**File:** `components/feed/MedalComposer.tsx:37-55`, `app/actions/send-kid-medal.ts:62-68`

**Issue:** `sendKidMedal` re-throws anything that isn't an `AuthError`:

```ts
try {
  member = await requireFamilyMember()
  await assertSiblingTarget(admin, member, params.targetChildId)
} catch (e) {
  if (e instanceof AuthError) return { success: false, error: e.message }
  throw e
}
```

`handleSend` in `MedalComposer.tsx` has a `try {...} finally {...}` around the
call with no `catch`, so any such re-thrown error (e.g. a Supabase network
failure inside `assertChildInFamily`) propagates as an unhandled promise
rejection out of the `onClick` handler. `setSending(false)` still runs (via
`finally`), so the button stops spinning, but the user sees no error message at
all — a silent failure — and the rejection surfaces only in the browser console.

**Fix:** Add a `catch` in `handleSend` that sets `setError(...)` for any
non-AuthError failure, matching the existing UX for the app-level error branch.

## Info

### IN-01: Redundant `family_members` lookup in `sendKidMedal`

**File:** `app/actions/send-kid-medal.ts:72-77`

**Issue:** `requireFamilyMember()` already resolves the caller's `user_id`; the
action then re-queries `family_members` by the same `user_id` purely to get
`id`/`display_name`, which is an avoidable extra round trip on every send.

**Fix:** Extend `Membership` (`lib/supabase/admin.ts`) to include `memberId` and
`displayName`, resolved in the same query `requireFamilyMember()` already runs,
and drop the second lookup here.

### IN-02: Duplicated sender identity in feed event metadata

**File:** `app/actions/send-kid-medal.ts:147-160`

**Issue:** `senderMemberId` is stored both as the row's `actor_member_id` column
(via `actorMemberId: senderMemberId`) and again inside `metadata.senderMemberId`.
Harmless, but redundant data that can drift if one is updated without the other
in a future edit.

**Fix:** Drop `senderMemberId` from `metadata` and read `actor_member_id` at
render time if it's ever needed alongside `senderRole`/`senderName`.
