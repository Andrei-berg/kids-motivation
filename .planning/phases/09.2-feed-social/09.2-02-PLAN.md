<objective>
Ship the whole server side of FEED-07: the `medals` schema change that makes the daily cap
sender-aware (D-09/D-10), the locked 8-phrase message set (D-11), and a new
`sendKidMedal` server action that lets a child recognize a sibling at **zero coins** (D-08)
with a sender-distinguishing feed event (D-12).

Purpose: FEED-07's remaining work is (a) letting a child trigger a medal at all, behind a
correct sibling-target auth guard, and (b) distinguishing kid-sent from parent-sent on the
card. No UI in this plan — plan 09.2-06 builds the composer against this action.

Output: one new migration (applied to the live DB in Task 2), `lib/kid/medal-phrases.ts`,
`app/actions/send-kid-medal.ts`, and a minimal, necessary edit to `app/actions/send-medal.ts`.

**Preserve-original-code rule (CLAUDE.md):** `sendMedal` keeps its parent flow — `requireParent`,
the 1–200 char freeform message, the 0–100 coin range, the wallet credit, its push, and its
existing `refId` — untouched. The only change to that file is making its daily-cap query and
its insert explicitly `sender_role = 'parent'`, which D-09 requires (otherwise a kid-sent medal
earlier in the day would block the parent's medal).

**Money rule (CLAUDE.md):** the kid path writes `medals` and `family_events` only, always
through `createAdminClient()` behind an auth guard, and must never import or call
`loadWallet`/`insertTx` or write `wallet`/`wallet_transactions`.

  <action>
**A. Create `app/actions/send-kid-medal.ts`** (`'use server'`). Mirror `send-medal.ts`'s shape
exactly; the differences are the guard, coins=0, the locked phrase set, the two caps, and the
sender-distinguishing emit.

Exported surface — in a `'use server'` file every exported function becomes a callable
endpoint, so export exactly one function plus type-only interfaces:
- `export interface SendKidMedalParams { targetChildId: string; phrase: string }`
- `export interface SendKidMedalResult { success: boolean; error?: string }`
- `export async function sendKidMedal(params: SendKidMedalParams): Promise<SendKidMedalResult>`
The sibling-target guard is a **module-local, non-exported** async function in this same file
(exporting it would publish a second server endpoint).

Flow:

1. **Phrase allow-list first.** `if (!isKnownMedalPhrase(params.phrase)) return { success: false, error: 'Недопустимое сообщение' }`.
   The client never supplies freeform text; this is the server-side enforcement of UI-SPEC
   content rule 2 (D-11).
2. **Identity.** `const admin = createAdminClient()`; inside a try/catch that maps `AuthError`
   to `{ success: false, error: e.message }` (and rethrows anything else, exactly as
   `sendMedal` does): `const member = await requireFamilyMember()`, then the local guard:
   - `member.role !== 'child'` → `throw new AuthError('Медаль брату или сестре может отправить только ребёнок', 403)`
   - `!member.childId` → `throw new AuthError('Профиль ребёнка не найден', 403)`
   - `member.childId === params.targetChildId` → `throw new AuthError('Нельзя отправить медаль самому себе', 403)`
   - `await assertChildInFamily(admin, params.targetChildId, member.familyId)` — the
     cross-family block; note this is the inverted twin of `authorizeChildAction`, which allows
     a child only on their own `childId`.
   Never accept a `familyId` from the caller: the family always comes from `member.familyId`
   (same rule as `sendMedal`'s "the client-supplied familyId is NOT trusted" comment — carry an
   equivalent comment into this file).
3. **Sender identity, server-derived.** Query `family_members` with the admin client:
   `.select('id, display_name').eq('user_id', member.userId).maybeSingle()`. Use its `id` as
   `senderMemberId`. `senderName` = `display_name?.trim()` or, when blank, the sender's own
   `children.name` (`admin.from('children').select('name').eq('id', member.childId)`), or
   finally the literal `Брат/сестра`. The client never supplies a sender name or role — D-12's
   copy must not be forgeable.
4. **`const today = localDateString()`** (never `toISOString().split('T')[0]`).
5. **Sender cap (D-10)** — `medals` where `sender_member_id = senderMemberId`, `date = today`,
   `sender_role = 'child'`, `.maybeSingle()`; if a row exists return
   `{ success: false, error: 'Ты уже отправил медаль сегодня' }` (this exact string is what the
   composer renders as its cap state — UI-SPEC Copywriting Contract).
6. **Recipient cap (D-09)** — `medals` where `child_id = targetChildId`, `date = today`,
   `sender_role = 'child'`, `.maybeSingle()`; if a row exists return
   `{ success: false, error: 'Этому ребёнку уже отправили медаль сегодня' }`. Do **not** filter
   out parent-sent rows by omitting `sender_role` — the whole point of D-09 is that a
   parent-sent medal the same day must not block this.
7. **Insert** into `medals`: `{ family_id: member.familyId, child_id: params.targetChildId, date: today, message: params.phrase, coins: 0, sent_by: senderName, sender_role: 'child', sender_member_id: senderMemberId }`.
   `coins` is the literal `0` (D-08) — no parameter, no settings lookup, no conditional.
   On error, map Postgres unique-violation `code === '23505'` back to the matching cap message
   (constraint `medals_kid_sender_day` → the sender message; `medals_recipient_day_role` → the
   recipient message) so a race between two concurrent taps degrades to the same friendly
   result rather than a raw DB error; any other error returns `{ success: false, error: insertError.message }`.
8. **No wallet work at all (D-08).** This file must not import `loadWallet`/`insertTx` from
   `@/app/api/wallet/_lib`, must not touch `wallet`, `wallet_transactions`, or `p2p_transfers`,
   and must not contain a `coins > 0` branch.
9. **Feed emit (D-12), non-fatal:**
   `void emitFeedEvent({ familyId: member.familyId, childId: params.targetChildId, kind: 'medal', title: 'Медаль от ' + senderName + ' 🏅', body: params.phrase, amount: null, icon: '🏅', refType: 'medal', refId: params.targetChildId + ':' + today + ':kid', mode: 'once', actorMemberId: senderMemberId, metadata: { senderRole: 'child', senderName, senderMemberId } }, admin)`.
   The `:kid` suffix keeps this row from colliding with a parent medal under the
   `family_events_dedup` unique key; `amount: null` keeps the card money-free (9.1 D-01).
   Deciding the title here is what makes D-12 work with **no** change to `EventRow`'s render.
10. **Push**, in a try/catch that only `console.warn`s on failure (mirror `sendMedal`):
    `notifyChild(params.targetChildId, '🏅 Медаль от ' + senderName + '!', params.phrase, '/kid/feed')`.
    There is no coin text — coins are always 0.
11. Return `{ success: true }`.

**B. Make the parent path sender-aware in `app/actions/send-medal.ts`** — two minimal edits,
nothing else in the file changes:
- the existing daily-cap query gains `.eq('sender_role', 'parent')` alongside its
  `child_id`/`date` filters, so a kid-sent medal earlier the same day no longer blocks the
  parent's medal (D-09);
- the existing insert object gains `sender_role: 'parent'` explicitly (the column default is
  also `'parent'`, but writing it makes the two paths symmetric and keeps the row correct if the
  default is ever dropped).
Do not change `requireParent`, the message length rules, the 0–100 coin range, the wallet
credit block, the existing `refId`, the push, or the return shape.
