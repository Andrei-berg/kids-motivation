Use these exact class and keyframe names — `globals.css` already defines generic `popIn`,
`slideUp` and `fadeIn`, so the `feed-` prefix is what keeps this phase from colliding with
them. Do not modify or reuse any existing keyframe. The `.feed-tease-reply` class is unused
until plan 09.2-05 renders the bubble; landing it here keeps `globals.css` out of that plan's
`files_modified` so the two plans never contend for this file.

**B. Retrigger the pop per chip in `EventRow`.** Add `const [popKey, setPopKey] = useState<Record<string, number>>({})`
inside `EventRow` (it is a function component in the same file; `useState` is already imported
at line 19). Add a local handler that bumps the counter and then delegates:
increment `popKey[emoji]` by 1 and call the existing `onReact(emoji)` prop — do not change
`onReact`'s signature, `toggleReaction`, or the parent's optimistic update.

Wire it into the chip loop:
- the chip's `onClick` calls the new local handler instead of `onReact` directly;
- read `const pop = popKey[emoji]` and set `className={pop ? 'feed-reaction-pop' : undefined}`;
- set `key={pop ? `${emoji}-${pop}` : emoji}`.

The changing `key` is what makes the animation replay on the second, third and fourth tap: CSS
animations do not restart when the same class is re-applied to the same DOM node, so the chip is
remounted instead. Guarding both `className` and `key` on `pop` being defined is required —
without it every chip would animate on first paint and on every feed refresh.

The animation is deliberately driven by the tap, not by the derived `mine` flag: the optimistic
update in `toggleReaction` means `mine` flips in the same commit anyway, and keying off the tap
keeps the pop on the chip the user actually touched even if the server write later fails.

Do not animate the 💬 comment button, the story bubbles, or the card.
