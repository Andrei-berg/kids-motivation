**2. `me` gains `childId`.** Change the state type from `{ id: string; name: string; role: string }`
to `{ id: string; name: string; role: string; childId: string | null }`, add `child_id` to the

**3. Tease state + initial load.** Add `const [teases, setTeases] = useState<Record<string, FeedComment[]>>({})`

per card and do not fetch them inside `CommentThread`.

**4. Route realtime comments.** The `subscribeFeed` `onComment` handler currently always
increments `commentCounts`. Change it to branch: when `isTeaseComment(c)`, append to
`teases[c.event_id]` unless a row with the same `id` is already present (the same
`some(x => x.id === …)` dedupe the `onReaction` handler uses, which is what keeps an optimistic
insert from doubling); otherwise increment the count exactly as today. A tease must never bump
the 💬 badge.

**5. `submitTease`.** Add an async function next to `toggleReaction`:
`async function submitTease(eventId: string, phrase: string)` — return early when `!familyId`
or `!me`; call `addTeaseReply({ eventId, familyId, authorMemberId: me.id, authorName: me.name, phrase })`;
when it returns a row, append it to `teases[eventId]` with the same id-dedupe. Do **not** write
an optimistic placeholder row before the insert resolves: unlike a reaction, a tease is
permanent and a rolled-back optimistic bubble would look like a delivered tease. The bubble
appearing on the server round-trip is the honest signal.

**6. Pass to `EventRow`.** Add three props at the call site: `teases={teases[e.id] ?? []}`,
`onTease={(phrase) => submitTease(e.id, phrase)}`, and keep everything else as-is. Declare them
in `EventRow`'s prop type (`teases: FeedComment[]`, `onTease: (phrase: string) => void`).
`FeedComment` is already imported as a type at line 33.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-092-24 | Tampering | Tease phrase content | mitigate | The tray only emits members of the locked 17, and `addTeaseReply` re-validates with `isKnownTeasePhrase` before writing; no text input exists in the flow (grep gate: the file's only `<input>` is the pre-existing comment box). |
| T-092-25 | Spoofing | Teasing as another member | mitigate | `authorMemberId`/`authorName` come from the session-resolved `me`, and the comments INSERT RLS policy independently requires `author_member_id` to be the caller's own `family_members.id`. |
| T-092-26 | Elevation of privilege | Cross-family tease | mitigate | `familyId` comes from the session-resolved membership, and the INSERT policy re-checks `family_id ∈ caller's families`. A tampered client cannot attach a tease to another family's event. |
| T-092-27 | Tampering | D-07 one-per-card bypass | accept | The cap is UI-level (`hasTeased` hides the tray) with no unique constraint on comments; a member using devtools could insert a second tagged row. Recorded rather than mitigated to avoid a migration for a cosmetic cap. |
| T-092-28 | Information disclosure | Rendering raw stored bodies | mitigate | Bubbles render `teaseTextOf(c)`, and `isTeaseComment` already required the text to be one of the 17 known phrases, so no arbitrary stored string reaches the bubble path. | T-092-SC | Tampering | npm/pip/cargo installs | mitigate | No package added; all styling is inline plus the two `globals.css` classes landed in 09.2-03. |
