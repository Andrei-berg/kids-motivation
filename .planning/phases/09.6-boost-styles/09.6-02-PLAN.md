<objective>
Add a `boostStyle` prop to `BoostDetailSheet` and mount the first of the two new detail-view bodies:
`quest-checklist`, a plain list of every boost condition (3 independent grade tiers + full-week +
streak×2 + streak×3) as its own row with its own reward and progress, plus one combined total row
(BOOST-04). The existing segmented-bar hero card is extracted into its own render function so the
two bodies live side by side with no shared-wrapper coupling (D-13).

Purpose: BOOST-04's success criterion is "every boost condition appears as its own row... plus one
combined total" — this plan is the entire quest-checklist implementation, reading exclusively from
the `BoostDetailView` fields plan 09.6-01 added (`grades.tiers`, `grades.nextTierIndex`,
`consistency.streak2Done/streak3Done/fullWeekCoins/streak2Coins/streak3Coins`) so BOOST-06 ("no
hardcoded sketch numbers") is true by construction.
Output: `BoostDetailSheet.tsx` gains a `boostStyle` prop, a `SegmentedBarBody` function (identical
behavior to today, just extracted), a `QuestChecklistBody` function, and a two-way render branch
(`quest-checklist` vs everything else). The `ring-badges` branch is added in plan 09.6-03 — until
then any `boostStyle` value other than `'quest-checklist'` renders `SegmentedBarBody`, matching this
project's own precedent for incremental style-branch construction (Phase 9.4's `KidDayFillForm.tsx`:
`tile-sheet` landed in one plan, `story-stepper` in the next, both against the same ternary chain).

Why this is its own plan: `QuestChecklistBody` is a genuinely new ~150+ line layout with its own
data-binding surface (6 independent conditions); bundling it with the also-new `ring-badges` body
(plan 09.6-03, ring + tier badges + popover + interaction state) in one plan would push a single
plan past the ~50% context budget. Same file, so this plan and 09.6-03 are sequential (wave 2 then
wave 3), not parallel — same-file-overlap rule.
</objective>
