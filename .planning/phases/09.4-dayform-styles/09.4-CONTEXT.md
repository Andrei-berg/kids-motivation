# Phase 9.4: dayform-styles - Context

**Gathered:** 2026-09-19
**Status:** Ready for planning

<domain>
## Phase Boundary

Build the two remaining day-fill interaction styles — `tile-sheet` (2-column grid of
per-category status tiles; tapping a tile opens a bottom sheet scoped to just that category)
and `story-stepper` (one category fills the screen at a time behind a dot-progress track,
auto-advancing with an explicit skip control) — as real, selectable options in the
`fill_style` preference, alongside the already-shipped `sticky-summary` default from Phase 9.3.

Both new styles are **new render/container shells over the exact same state, validation,
save, and `/api/wallet/award` logic already in `KidDayFillForm.tsx`** (the same reuse
principle Phase 9.3 established as D-13) — no new coin math, no new data model, no changes
to `sticky-summary` itself. The real category list (room, individual extra activities,
individual custom day-blocks, grades, sport/coach-rating, reading, behavior, mood) and its
existing body JSX (`roomBody`, `extraActivitiesBody`, `gradesBody`, `exercisesBody`,
`sectionsBody`, `readingBody`, `behaviorBody`) carry over unchanged into both new shells —
tile-sheet wraps each body in a bottom sheet, story-stepper wraps each body in a full-screen
step.

Out of scope: `sticky-summary` (done), `boost_style`/weekly-boost detail views (Phases
9.5/9.6), and a loot-box/crate reward mechanic raised during discussion (see Deferred Ideas)
— that is a new economy feature, not a day-fill interaction style.

</domain>

<decisions>
## Implementation Decisions

### Tile-sheet: tile granularity
- **D-01:** Every individual real-data item gets its own tile — each extra activity and each
  custom day-block is its own one-tap-to-open tile with its own status, not grouped under a
  shared "Activities"/"Custom" tile. Mirrors 9.3's D-05 broadening (any category whose real
  data shape is a simple per-item yes/no gets individual treatment). The grid can legitimately
  run to 8-12+ tiles for a family with several activities/custom blocks configured.
- **D-02:** Mood gets its own tile in the grid (not a pinned strip outside it) — tapping opens
  a sheet containing the same 5-emoji picker + "wow" pop animation (9.3 D-08) used in
  sticky-summary. Keeps the grid's "every category visible as a tile" promise consistent even
  though mood has no coin value.
- **D-03:** Room, grades, sport, reading, and behavior each get exactly one tile (their
  existing body JSX renders inside that tile's sheet) — this mirrors sticky-summary's existing
  category boundaries (9.3 D-05/D-06/D-07), just re-expressed as "tile → sheet" instead of
  "one-tap-row" / "inline-panel".

### Story-stepper: step granularity
- **D-04:** Individual activities are grouped into **one** "Activities" step (a checklist of
  all activities shown together on that screen); individual custom blocks are similarly
  grouped into **one** "Custom" step. This is the opposite grain from tile-sheet (D-01) —
  deliberate, to keep total step count reasonable for a linear one-screen-at-a-time flow
  (variant B's intended pacing) rather than ballooning to 15+ steps.
- **D-05:** Mood gets its own full-screen step (not a persistent strip alongside the stepper)
  — the "wow" pop animation plays on that step when an emoji is tapped, then the step
  auto-advances like any other step (per D-06/D-07 below).
- Room, grades, sport, reading, and behavior each get their own step, same category
  boundaries as tile-sheet's D-03 and sticky-summary's existing boundaries — just one category
  per full screen instead of one category per sheet/panel.

### Persistent progress display
- **D-08:** Tile-sheet shows the exact same `StickySummaryBar` component (ring + ticking coin
  total) above the tile grid, reusing sticky-summary's header as-is — no new header component.
- **D-09:** Story-stepper shows a **small persistent coin total** in a slim header above the
  dot-progress track (not a full ring — the dots themselves already convey completion %). This
  keeps DAYFORM-05's "ticking running total" visible throughout the flow, not just at the end.

### Story-stepper navigation & skip
- **D-10:** Auto-advance always walks through every *applicable* category (the same
  applicable-map from 9.3's D-09 — a category with nothing configured for this child is
  excluded from the sequence entirely, not shown as an empty step) — it never silently
  auto-skips an applicable step just because nothing was entered. A step left blank stays
  blank; leaving it is the explicit skip control's job (D-11), not an automatic heuristic.
- **D-11:** The skip control only advances to the next step — it does not write/mark anything
  for the skipped category, and that category's dot stays in its normal not-done state
  (no third "skipped" dot state). The category remains freely revisitable later via D-12.
- **D-12:** The dot-progress track is tappable — the kid can tap any earlier dot to jump back
  to that step and change an answer, Instagram-Stories-style. This is story-stepper's
  equivalent of the re-tappability every other style already has (9.3's D-10 for binary rows,
  tile-sheet's tap-to-reopen-a-sheet).

### Locked days & final save
- **D-13:** A locked past day renders in the child's chosen style but read-only: tile-sheet's
  grid still shows tiles, but tapping one opens its sheet with no toggle/edit controls;
  story-stepper still shows the dot-track, but tapping a dot opens that step read-only (no
  auto-advance/skip UI, since nothing can change). The kid always sees their own preferred
  style, including when reviewing a past day — no fallback to sticky-summary's locked view.
- **D-14:** Tile-sheet's final save uses the exact same pinned-above-bottom-nav Save button
  already built for sticky-summary (same component/position, same "can save partially filled,
  reopen and finish later" behavior as today — no new completion gate).
- **D-15:** Story-stepper lands on a short summary screen (recap + coin total, mirroring
  sticky-summary's save button) after the last applicable step, rather than auto-saving
  immediately — giving one last look/edit-via-dots chance before the explicit Save tap credits
  coins. No style ever auto-submits without an explicit save action.

### Coin feedback & tile visual details
- **D-16:** The floating +N/-N coin feedback anchors at the actual tap point inside the sheet
  (tile-sheet) or step (story-stepper) — reusing 9.3's exact `data-fill-row` +
  `onPointerDownCapture` anchoring mechanism, not a fixed position near the header total. Same
  mechanism, just needs `data-fill-row` markers inside the new sheet/step bodies.
- **D-17:** A tile-sheet tile shows a distinct loss tint (red/muted, mirroring 9.3's D-11) when
  its category nets negative coins today (e.g. a low grade, a poor coach rating) — not just a
  binary mint-done/neutral-not-done state. Same transparency principle as D-11: "every action
  has a visible, honest consequence."
- **D-18:** Every tile-sheet bottom sheet requires an explicit close (X / swipe-down) regardless
  of category — no auto-close on a single-tap answer (e.g. picking a mood emoji does not
  immediately dismiss the sheet). One consistent close behavior across every sheet, no
  per-category branching.

### Claude's Discretion
- Exact bottom-sheet open/close transition timing/easing beyond the sketch's
  `translateY(100%)` → `translateY(0)` pattern (`.28s cubic-bezier(.2,.9,.3,1.1)`) — follow the
  sketch's CSS as the base, minor tuning is implementer's call.
- Exact dot-track visual treatment for the "current" vs "done" vs "not-yet-visited" states
  beyond the sketch's `.dot`/`.dot.current .fill` pattern (sky for current, mint for done).
- Whether the story-stepper's persistent coin-total header (D-09) sits above or is integrated
  into the same row as the dot-track — implementer's call on exact layout, as long as both are
  visible together throughout the flow.
- Exact wording/visual of the skip control (icon-only vs "Пропустить" label) and of the
  end-of-stepper summary screen's recap content (list of what was filled vs just the total) —
  implementer's call, staying within existing i18n/copy patterns.
- Whether tile-sheet's grid uses a fixed 2-column layout at every viewport width or reflows —
  the requirement (DAYFORM-02) says "2-column grid" explicitly, so this is really just a
  confirmation that no responsive reflow is expected, not an open question.

</decisions>

## Existing Code Insights

### Reusable Assets
- All of `KidDayFillForm.tsx`'s existing state, handlers, `sectionCoins`/`coinsPreview`,
  `applicable` map, `progress`, and the 7 body JSX blocks — zero changes needed to any of this
  for either new style; only new container/renderer functions consume them
- `StickySummaryBar` — drop-in reuse for tile-sheet's header (D-08)
- `useCoinAnimation`/`CoinFlyup`/`onPointerDownCapture` anchoring — drop-in reuse for both new
  styles' floating feedback (D-16), same `data-fill-row` marker convention

### Established Patterns
- "Plain function, not nested component" renderer idiom (`renderGroup`/`renderPanelRow`/
  `InlinePanelRow`'s doc comment) — mandatory for any new `TileCard`/`StepScreen` renderer so
  controlled inputs (grade buttons, reading text fields) inside the reused bodies never remount
- Reduced-motion double-guard (CSS keyframe behind `prefers-reduced-motion: no-preference` +
  post-mount JS `reduced` state check, established in 05.3-02 and reused by 9.3's mood-pop) —
  applies to any new sheet-slide-up and dot-fill-transition animation
- Per-child settings self-serve write pattern (`requireFamilyMember` + `authorizeChildAction`
  + service-role `createAdminClient`) already implemented in `fill-style.ts` — no new pattern
  needed, just remove the Phase-9.3-scope guard (D-01 note above)

<deferred>
## Deferred Ideas

- **Loot-box/crate reward mechanic** (raised during this discussion): a Brawl-Stars-style
  reward crate system with variable rarity, given for weekly achievements, containing bonuses
  similar to the existing shop's rewards, plus a "chaos"/higher-variance crate tier. This is a
  new economy/reward-delivery capability, not a day-fill interaction style — out of scope for
  Phase 9.4. Not yet placed on the roadmap; would need its own future phase (likely v6.0
  Monetization territory, or a new phase inserted into a future milestone) and dedicated
  discussion covering: `wallet_settings`/`rewards` schema implications, drop-rate fairness and
  transparency (this app's core "every action has a visible, honest consequence" principle
  cuts against opaque randomness), and whether a randomized-reward mechanic raises any
  COPPA-adjacent "directed at children" concerns alongside the existing consent-gate work from
  Phase 4.4.

</deferred>
