<objective>
Build the data layer the segmented-bar detail view binds to: surface the grades-only hint string from
`computeWeeklyBoost`, expose the raw `BoostSettings`/`WeeklyGradeStats`/`WeeklyConsistencyStats`
inputs from `getBoostProgress`, and add a pure, unit-tested `buildBoostDetail` view-model builder
that turns them into fractional fills, the penalty state and the two consistency zone booleans.

Purpose: BOOST-03 (two independent sub-bars each with its own hint), BOOST-06 (every threshold and
amount read live from `lib/kid/boost-rules.ts`, none of the sketch's placeholder numbers), and
CONTEXT decisions D-04 (fractional not stepped), D-05 (penalty is a distinct state, never a bare 0%),
D-06 (two independent zones, not summed), D-07 (total = `week.total`).
Output: three pure/typed modules plus a test file. No React, no component, no UI in this plan — the
rendering ships in plan 03.

Why this is its own plan: putting the numeric rules in a pure module with real tests is what makes
"no hardcoded sketch numbers" (BOOST-06) provable by an automated gate rather than by reading JSX.
</objective>

```typescript
export const PENALTY_FILL_PCT = 40

export interface BoostWeekDetail {
  settings: BoostSettings
  grades: WeeklyGradeStats
  consistency: WeeklyConsistencyStats
}

export interface BoostDetailView {
  grades: {
    penalized: boolean          // D-05 — a penalty grade zeroed the whole grades bonus
    pct: number                 // 0..100; PENALTY_FILL_PCT when penalized
    tierReached: 0 | 1 | 2 | 3
    tierTotal: 3
    nextThreshold: number | null   // count needed for the next tier; null at tier 3
    nextThresholdUnit: 'top-grades' | 'graded-days' | null
    topGradeCount: number
    coins: number               // === week.grades
  }
  consistency: {
    fullWeekDone: boolean
    filledDays: number
    fullWeekTarget: 7
    streakDone: boolean
    streaksAtThreshold: number
    streakTarget: number        // 2 — consistencyBoost()'s boost_streaks_2 threshold
    bonusesEarned: 0 | 1 | 2
    bonusesTotal: 2
    coins: number               // === week.consistency
  }
  total: number                 // === week.total
}

export function buildBoostDetail(detail: BoostWeekDetail, week: WeeklyBoostResult): BoostDetailView
```

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-095-06 | Tampering | `buildBoostDetail` coin amounts | mitigate | The builder copies `week.grades`/`week.consistency`/`week.total` verbatim and never recomputes a coin amount, so a display bug cannot invent a payout that differs from `computeWeeklyBoost` — the same function the award route uses. Asserted by the `<behavior>` cases comparing against the passed `WeeklyBoostResult`. |
| T-095-07 | Spoofing | client-visible boost totals | accept | `lib/kid/boost.ts` is a pure display read; a user tampering with it in their own browser changes only what they see. `/api/wallet/award` recomputes server-side from saved rows with `(child_id, source_type, source_id)` idempotency and is unaffected by this plan. |
| T-095-08 | Information Disclosure | `weekDetail` raw stats in the client payload | accept | `filledDays`, `topGradeCount`, `hasPenaltyGrade` and `streaksAtThreshold` are the child's own data, already readable by that child through the existing family-isolated `subject_grades`/`days`/`streaks` queries in the same function. No new row or column is exposed and no cross-family read path is added. |
| T-095-09 | Tampering | additive change to `WeeklyBoostResult` | mitigate | Only a new key is added; `grades`/`consistency`/`total`/`max`/`nextLabel` are untouched, so `/api/wallet/award`'s use of `computeWeeklyBoost` cannot shift. Guarded by `npm test` staying green and by the acceptance criterion that no existing return field changes. |
| T-095-SC | Tampering | npm/pip/cargo installs | accept | No new dependency is added by this plan — `lib/kid/boost-detail.ts` imports only from `./boost-rules`, and the test uses the repo's existing vitest. Nothing for the Package Legitimacy Gate to audit. |
