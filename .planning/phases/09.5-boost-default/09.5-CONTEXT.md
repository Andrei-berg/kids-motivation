# Phase 9.5: boost-default - Context

**Gathered:** 2026-09-20
**Status:** Ready for planning

<domain>
## Phase Boundary

Add a persisted, changeable per-child `boost_style` preference (`segmented-bar` /
`quest-checklist` / `ring-badges`), and build **segmented-bar** as the first real, tappable
weekly-boost detail view: tapping the existing inline `BoostMeter` (wherever it appears) opens
a bottom sheet showing the grades-tier progress and the consistency-bonus progress as two
independent sub-bars, each reading real thresholds/amounts from `lib/kid/boost-rules.ts` — no
hardcoded sketch placeholder numbers.

`quest-checklist` and `ring-badges` (BOOST-04/05) are **not built in this phase** — they belong
to Phase 9.6, which depends on this phase. This phase only needs the `boost_style` preference
field/control to exist (BOOST-01) and `segmented-bar` itself to be fully real (BOOST-02, BOOST-03,
BOOST-06 as they apply to this one style).

The inline `BoostMeter` itself (`components/kid/design/atoms.tsx`) stays visually unchanged —
this phase only makes it tappable and builds what opens behind the tap. Milestone tiers
(`/kid/achievements`) are out of scope — they are a separate, already-shipped display, not part
of the weekly boost detail view.

</domain>

<decisions>
## Implementation Decisions

### Tap target & container
- **D-01:** All three existing `BoostMeter` instances become tappable: the Day hero full version,
  the Day hero compact version, and the `ProfileSheet` version (`components/kid/ProfileSheet.tsx`
  line ~145, `app/kid/(app)/day/page.tsx` lines ~335 and ~404). Every place a kid sees the meter,
  tapping it opens the same detail view — no inconsistent subset.
- **D-02:** The detail view opens in a **`BottomSheet`** (reuse the exact component built in Phase
  9.4, `components/kid/day-fill/BottomSheet.tsx`), not a new full-screen route and not a new modal
  pattern. Rationale (explicit "build with headroom" ask): `BottomSheet` is a content-agnostic
  shell — it renders whatever body is passed to it. Phase 9.6's `quest-checklist` and
  `ring-badges` bodies plug into the exact same sheet/open-mechanism without touching the entry
  points wired in this phase.
- **D-03:** Closing follows the same explicit-close rule as Phase 9.4's `BottomSheet` usage (X /
  swipe-down) — no backdrop-tap-to-close deviation.

### Segmented-bar content mapping (real formula → 2 sub-bars)
- **D-04:** "📚 Оценки" sub-bar fills as **fractional progress toward the next tier** —
  `topGradeCount / <next threshold>` (0 at 0 top grades, full at `boost_grades_t1_count`, etc.),
  not a stepped 0/33/66/100% tier-only fill. This mirrors the granularity already promised by the
  existing `nextLabel` hint text ("ещё N пятёрок → +X").
- **D-05:** When `hasPenaltyGrade` is true (a single penalty grade zeroes the whole grades boost
  regardless of how many top grades were earned), the sub-bar shows a **distinct visual status**
  (muted/red tint, not the normal mango fill) plus an explicit hint explaining a penalty grade
  zeroed the bonus — never a plain "0%" that reads as "no good grades yet." This follows the
  product's transparency principle (PROJECT.md: every consequence must be visible and honest, not
  hidden) — same principle already applied to loss-feedback in Phase 9.3's D-11.
- **D-06:** "🔥 Стабильность" is **one bar with two independent internal fill zones** — one for
  full-week completion (binary: 7/7 days), one for streak-tier (0/2/3, not summed) — each zone
  fills/colors on its own, plus two small status chips under the bar ("7/7 дней" done/not-done,
  "стрик×N" done/not-done) so neither condition reads as swallowed into a single percentage. Fill
  transition reuses the sketch's validated spring easing (`cubic-bezier(.2,.9,.3,1.1)`); a segment
  completing gets a subtle glow-pulse (respecting the existing reduced-motion double-guard
  pattern from 05.3-02, reused by 9.3's mood-pop and 9.4's sheet transitions) — exact pulse
  timing/intensity is implementer's call.
- **D-07:** Below the two sub-bars, an explicit **total row** sums both bars
  (`= boost.week.total`), matching the number already shown on the inline `BoostMeter` — gives the
  kid a direct visual link between the summary meter and the detail breakdown.

### Empty/zero-week state
- **D-08:** No new UI state for "start of week" (0 grades, 0 filled days) — both sub-bars simply
  render at their normal 0% with their normal hint text (already self-explanatory: "ещё 5 пятёрок
  → +150"). No separate branch/component. A tasteful empty-state visual touch (e.g. a subtle
  shimmer/pulse on the empty track inviting the first fill) is allowed as an implementer-level
  detail using existing CSS idioms — not a new state machine or new copy.

### `boost_style` control placement & default
- **D-09:** `boost_style` is **unified into the same "Style" section in `ProfileSheet` as
  `fill_style`** — one section with two picker rows (Day-fill style, Boost style) instead of two
  separate blocks. Same self-serve pattern as `fill_style`: `children.boost_style` column
  (mirrors `fill_style`'s migration shape), a new server action mirroring
  `app/kid/actions/fill-style.ts` exactly (`requireFamilyMember` + `authorizeChildAction` +
  service-role `createAdminClient`, string + whitelist validation before any auth/DB work), and a
  radiogroup control in `ProfileSheet.tsx` next to the existing `fill_style` radiogroup.
- **D-10:** In this phase, the `boost_style` picker shows **only `segmented-bar`** as a real,
  selectable option (mirrors Phase 9.3's D-01 for `fill_style`: no "coming soon" UI for
  `quest-checklist`/`ring-badges`, they appear once Phase 9.6 ships). Schema default is
  `segmented-bar` (`TEXT NOT NULL DEFAULT 'segmented-bar'` + CHECK constraint, mirroring the
  `fill_style` column pattern).

### Claude's Discretion
- Exact glow-pulse timing/intensity on the "🔥 Стабильность" bar segment completion (D-06) —
  follow the sketch's `.seg-fill` transition as the base, tune the pulse within the existing
  reduced-motion guard.
- Exact shimmer/pulse treatment (if any) for the empty-week state (D-08) — implementer's call,
  must not introduce a new state branch.
- Exact wording of the penalty-disqualified hint text (D-05) beyond "a penalty grade zeroed this
  week's grade bonus" — implementer's call within existing i18n/copy patterns.
- Whether the `boost_style` migration is bundled with this phase's first plan or split out — no
  product-level ambiguity, purely a migration-sequencing call mirroring `fill_style`'s migration.

</decisions>

## Existing Code Insights

- `BottomSheet` (Phase 9.4) — drop-in reuse for the detail-view container (D-02)
- `app/kid/actions/fill-style.ts` — copy-paste-adapt template for the new `boost-style.ts` action

### Established Patterns
- Per-child settings columns follow the `fill_style`/`backfill_mode` shape: additive `ALTER TABLE
  children ADD COLUMN IF NOT EXISTS ... TEXT NOT NULL DEFAULT '...'` + idempotent `DO $$ ...
  CHECK (...) $$` constraint block
- Self-serve kid-controlled settings (`fill_style`, `avatar_kind`) always go through a `'use
  server'` action with `requireFamilyMember()` + `authorizeChildAction()` + service-role
  `createAdminClient()` — never a direct client `.update()` on `children`
- Reduced-motion guard pattern (keyframe behind `prefers-reduced-motion` + post-mount JS check,
  established 05.3-02, reused by 9.3's mood-pop and 9.4's sheet/dot transitions) — applies to the
  segment glow-pulse (D-06)

### Integration Points
- `lib/kid/boost.ts`'s `getBoostProgress()` — needs its return shape extended so callers (Day
  page, `ProfileSheet`, and the new detail sheet) can access the raw grade/consistency stats
  needed for fractional sub-bar rendering, not just final coin totals
- `components/kid/ProfileSheet.tsx` and `app/kid/(app)/day/page.tsx` — the 3 existing `BoostMeter`

## Specific Ideas

- User asked for the "🔥 Стабильность" bar and the empty-week state to feel satisfying/delightful
  ("сделай чтобы вау") without specifying exact visuals — resolved by proposing a two-zone bar
  with spring easing + completion glow-pulse (D-06) and a tasteful empty-state shimmer (D-08),
  both confirmed by the user as acceptable, with exact tuning left to implementation.

</specifics>
